# 版本

[English](09-versions.md) | [简体中文](09-versions.zh-CN.md)

## 功能

**版本** 列出 fit 应用过的配置：每次应用都留下一个版本，最新的在前，保留的数量由 `admin.history` 决定
（默认 10，运行中的那份也算在内）。这一页读的是 Admin API 的 `GET /versions`（在控制台上是
`GET /api/m/admin/versions`），所以它显示的是真正应用过的配置，不是草稿。

版本是 fit 这个进程记住的一份清单：重启后从"fit 启动时用的那份配置"重新开始，所以清单里前几个版本来自这次
运行。有 store 时，每次应用都会把配置写进 store；这一页保留的是内存里的清单，不是 store 的历史。

这一页做两件事：**查看**一个版本的文本，**回滚**到它。回滚不会抹掉历史：它把旧配置再应用一次，作为一个新的
版本，所以回滚本身也在版本列表里，也能再回滚。这一页的价值在于可以撤销与核对：改坏了可以回到上一份；想知道
某次应用到底写了什么，可以读它的文本。

## 页面与操作

### 配置版本

页面顶部的一行说明：已应用的配置，最新的在前，保留数量由 fit 决定；回滚即把旧版本重新应用为新版本。接口按最老
的在前返回，页面把它倒过来显示。下面是一张表，每行一个版本：

| 列 | 显示什么 |
| --- | --- |
| 版本 | 版本号；运行中的那一行带一个**运行中**的徽标 |
| 应用时间 | 应用的时刻，旁边是多久之前 |
| 来源 | 这份配置从哪来：`file`、`admin`（经控制台或 Admin API 改的）、`rollback`，或某个 provider 的名字 |
| 大小 | 配置写出的字节数 |
| ETag | 它的强实体标签：配置内容的哈希，`If-Match` 比较的就是它 |

例如：

| 版本 | 应用时间 | 来源 | 大小 | ETag |
| --- | --- | --- | --- | --- |
| 12 · 运行中 | 2026-11-08 14:02:11（3 分钟前） | `admin` | 1.2 KiB | `"9f2c1a7b3e0d4c65a1b8e2f0"` |
| 11 | 2026-11-08 13:47:02（18 分钟前） | `docker` | 1.1 KiB | `"3b7e5c2a9d1046f8c3e5a2b1"` |
| 10 | 2026-11-08 11:20:44（2 小时前） | `rollback` | 1.0 KiB | `"7a1d4e8b2c3059f6a4d8e1b7"` |

**刷新** 重新读取这张表；表在打开这一页时读一次。这一页不编辑任何成员，所以没有格式标签页，但仍有共用的保存
栏：回滚带 `If-Match` 发送，比较的是运行中配置的 ETag。失败的应用不留下版本：只有走通的应用才被记下，失败的
次数在[概览](04-overview.zh-CN.md)页的突增里能看到。Admin API 的仪表盘也显示这些版本（`admin.disable_dashboard`
关掉仪表盘时就不显示了）。

**查看** 打开一个窗口，标题是"版本 N"，显示那个版本的文本：能解析成 JSON 就格式化后显示，否则按写出的样子
显示。窗口里有**复制**、**回滚**（只有不是运行中的版本才有）和**关闭**。文本是那份配置本身——基础配置，不含
provider 提供的内容；要看合并后的，去 [JSON](08-json.zh-CN.md) 页的生效配置标签。

这一页与[概览](04-overview.zh-CN.md)页的关系是：概览只显示运行中的版本与它的来源，这一页列出全部保留的版本。

**回滚** 要确认两次：草稿里有未保存的修改时先问"回滚会放弃尚未保存的修改。继续？"，再问"将版本 N 重新应用为
一个新版本？"。确认后走与保存相同的路径：先校验，再应用为一个新版本并写入 store，成功后提示"版本 N 已重新应用
为版本 V"，表随之刷新。新版本的来源是 `rollback`，它保留原版本的来源；provider 提供的内容按当前的重新合并。
版本不再被保留（超出 `admin.history`）时，`GET /versions/{n}` 答 404，页面上也就没有它的行。

这一页不显示是谁做的：记下"哪个用户、从哪里的登录、应用了哪个版本"的是 `admin` 日志器。

这一页用到的接口（Admin API 的接口在控制台上都在 `/api/m/admin/` 下）：

| 接口 | |
| --- | --- |
| `GET /versions` | 保留的版本，最老的在前，加运行中的版本号 |
| `GET /versions/{n}` | 版本 n 的文本 |
| `POST /rollback/{n}` | 把版本 n 再应用一次，带 `If-Match` |

## 参数

这一页只涉及 `admin` 的一个字段，而 `admin` 从不在控制台页面上编辑：它来自引导文件。

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `admin.history` | 10 | 保留多少个已应用的配置供读回，运行中的那份算在内；0 或留空取 10 |

一个版本记的东西（`GET /versions` 的每一项）：

| 字段 | 说明 |
| --- | --- |
| `version` | 运行时的图给出的版本号 |
| `applied` | 应用的时刻 |
| `source` | 从哪来：`file`、`admin`、`rollback` 或某个 provider 的名字 |
| `bytes` | 配置写出的字节数 |
| `etag` | 内容的哈希（前 12 字节，十六进制，带引号），作为强实体标签 |

完整表：[admin](../reference/config.md#admin-api)。

保留的是这个进程内存里的清单：超出 `admin.history` 的最老的被丢弃，运行中的那份总在（至少保留一个）。

## 版本与 store

store 里只有一份配置：当前那份。每次应用都会把它写进 store（有 store 时），所以回滚之后 store 里就是回滚的
那份；版本清单是 fit 这个进程在内存里记的，重启后从启动用的那份重新开始。

`fit store export` 与 `fit store import` 读写的是 store 文件，与这一页的版本清单无关：导出的是运行中的配置，
导入走的是保存的路径。没有 store 时，控制台像 Admin API 一样在内存中改配置，重启后从配置文件重新开始，这一页
显示的仍是这次运行应用过的版本。

## 回滚走的路径

回滚是一次应用：那份配置被加载、编译，新的监听地址被试绑，然后才应用；任何一步失败，运行中的配置保持不变。
`If-Match` 比较的是运行中配置的 ETag，不匹配（`412`）时什么都不应用。

成功后：一个新的版本、写入 store、`admin` 日志记下这次应用。回滚只把那份基础配置再应用一次，不改 provider
提供的部分；它也不会重启只在启动时读取的设置——`engine`、`telemetry`、`providers` 与 `admin` 要到下次重启才
按新的值跑，这类差异在[一致性检查](10-consistency-check.zh-CN.md)页上能看到。

## 常见情形

- **改坏了，回到上一份**：找到上一个来源为 `admin` 的版本，**查看**确认它的文本，再**回滚**。回滚前草稿里的
  未保存修改会被放弃，所以先在 [JSON](08-json.zh-CN.md) 页复制下来，或先保存。
- **看某次应用到底写了什么**：版本的文本是那份配置本身，不含 provider 提供的内容；两者一起看要看生效配置。
- **重启之后清单变了**：这次运行应用过的版本才是页面上有的；重启后从启动用的那份重新开始。要留一份配置在
  机器上，用 `fit store export` 或 [JSON](08-json.zh-CN.md) 页的下载。
- **来源是 provider 名的行**：那是 provider 提供的内容变化时的一次应用。版本记的文本仍是基础配置本身，provider
  的部分在生效配置里看；同样的内容不会重复应用，所以不会重复产生版本。
- **回滚与重新应用的区别**：一致性检查里的 `reapply` 再应用的是当前的配置，回滚再应用的是某个版本写出的那份；
  两者走的是同一条路径。
- **回滚前先看**：先**查看**确认那份文本，再回滚；确认后没有反悔，因为它是一次应用。
- **回滚前想想 `If-Match`**：它比较的是运行中配置的 ETag，不是某个版本的 ETag；回滚期间配置被别处改过，会得到
  `412`，什么都不应用。
- **对比两个版本**：这一页没有并排比较；用**查看**复制一份文本，再与另一份比。
- **回滚不改 `admin`**：`admin` 来自引导文件，每次加载时被放进配置；用户、密码与 store 的设置不在版本里，所以
  回滚不会动它们。
- **脚本里读版本**：终端里没有读版本的命令，要读它用 Admin API：
  `curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:2019/versions`；回滚是
  `POST /rollback/{n}`，带 `If-Match`。
- **管理端**：`admin.cluster` 的回滚是对每个成员调用它的 `POST /rollback/{n}`，所以管理端上看到的版本是那个
  成员自己的版本。

## .conf 配置

这一页不编辑任何成员，所以没有 `.conf` 示例：它读的是已经应用过的配置。`admin` 从不在控制台页面上编辑，它来自
引导文件（[第 01 章](01-deployment.zh-CN.md)）。
