# 026: A VPN of fit nodes, direct where a hole can be punched and relayed over QUIC, WebSocket or HTTP/2 where not

[English](026-vpn.md) | [简体中文](026-vpn.zh-CN.md)

Status: accepted (2026-11-01).

## Context

fit is to join hosts into one private network: each node gets an address in an overlay network and
a TUN interface, and IP packets go between nodes as if they shared a LAN, as Tailscale and ZeroTier
do. Nodes are mostly behind NAT. Two nodes talk directly through a hole punched in both NATs
([decision 025](025-p2p.md)'s ICE); where no hole can be punched, or a node is configured not to
try, the packets go through a server node. Networks that block UDP, or let only HTTPS out, are
common, so the relay must be reachable over QUIC, WebSocket and HTTP/2, tried in a configured
order, falling back to the next when one fails, and a node's transport can also be chosen by hand
on the web page.

## Decision

- **Built on the P2P milestone (I84–I93).** Discovery and hole punching are `p2p/ice` and
  `p2p/stun`; the payload between two nodes is the same QUIC connection over the selected pair, with
  certificate fingerprints exchanged through the server, as in decision 025. TURN stays available
  as ICE's relayed candidates for networks that pass UDP; the relay this note adds is for those that
  do not, and is the VPN's default.
- **Packages.** `vpn/packet` (IP headers and the overlay route table), `vpn/tun` (the TUN device on
  each OS), `vpn/relay` (the relay protocol, the relay server, and the client that picks a
  transport), and `vpn` (the node, the coordinator and the config's apps).
- **IP packets are QUIC DATAGRAM frames** (RFC 9221, fib request A50) on the end-to-end QUIC
  connection between two nodes: unreliable and unordered, so a lost packet is lost as on a wire and
  TCP inside the tunnel recovers it, with no head-of-line blocking and no TCP-over-TCP retransmits
  on a direct or QUIC path.
- **The relay carries the end-to-end QUIC connection's packets, not IP packets.** To a node the
  relay is one more `quic.PacketConn` path toward a peer, as a TURN allocation is: the server
  forwards opaque QUIC datagrams by node ID and cannot read or alter the traffic (TLS 1.3 end to
  end). A pair of nodes starts on the relay at once, while ICE checks run, and moves to the direct
  path by QUIC's path migration once ICE nominates a pair; when the direct path fails consent, it
  moves back. Nothing above QUIC sees the change.
- **One relay protocol over three transports.** A frame is a type byte, a varint node ID and a
  payload: `DATA` (to the peer named, or from the peer named when the server delivers it), `GONE`
  (the peer has no session), `PING` and `PONG`. The server sets the source ID from the session's
  authenticated node, so a node cannot speak as another. Framing per transport:
  - **QUIC**: a QUIC connection to the server; `DATA` frames as DATAGRAM frames, so nested QUIC is
    not made reliable twice; the others on one bidirectional stream, length-prefixed.
  - **WebSocket**: one binary message per frame, at a configured path on the server's HTTPS
    listener (HTTP/1.1 upgrade, or RFC 8441 over HTTP/2 where the client has it).
  - **HTTP/2**: an extended CONNECT stream (`:protocol` `fit-relay`), frames length-prefixed
    (16-bit) on it. It needs fib's HTTP/2 client CONNECT streams, F1 of the
    [mesh roadmap](../mesh-roadmap.md) (iteration S04).
  Over WebSocket and HTTP/2 the inner QUIC still runs its congestion control; it sees delay, not
  loss, as Tailscale's DERP and every TCP fallback do.
- **The transport is chosen in order, with fallback.** A node's `relay.transports` lists the
  transports to try, by default `[quic, websocket, http2]`. The client dials the first with a
  connect timeout (5 s), and on failure the next; a session that ends starts again from the top
  with backoff. On a transport that is not the first, the client probes the ones ahead of it every
  probe interval (60 s) and moves to the first that answers, opening the new session before closing
  the old one, so the inner QUIC connections see a path change and not a loss.
- **A node's transport can be fixed by hand.** `relay.transport` is `auto` (the order above) or one
  transport, which is then the only one tried, retried with backoff and shown as failing if it
  fails. It is set in the node's config, on the node's own web page, or for any node on the server's
  web page, which delivers it in the node's netmap; the node's own setting wins when both are set,
  and the page shows which one is in force. The web pages are fit's admin dashboard, and changes go
  through the Admin API and its config versions like any other.
- **Direct connections can be turned off per node.** `p2p: false` on a node, or on the server for
  that node, skips ICE, and the node's peers reach it through the relay only.
- **The coordinator is the server node.** It is a fit with the relay server and I92's signaling
  endpoint. Nodes join with a token, are given an overlay address from the configured network
  (IPv4 and IPv6), and get a netmap: every peer's node ID, overlay addresses, routes it serves,
  certificate fingerprint, and the per-node settings above, pushed again when anything changes.
  Relay sessions authenticate with a short-lived ticket the coordinator signs for the node.
- **Routes are checked both ways.** A packet read from the TUN goes to the peer whose prefix holds
  its destination (longest prefix wins); a packet from a peer is written to the TUN only if its
  source is in that peer's prefixes, as WireGuard's cryptokey routing does. A node may serve
  further prefixes (a subnet router) the coordinator approves.
- **The MTU fits the path.** The TUN's MTU is 1280 by default, IPv6's minimum, which leaves room for
  two layers of QUIC on a 1500-byte path; it can be set. A packet larger than a peer's DATAGRAM
  limit is dropped with ICMP Fragmentation Needed or Packet Too Big written back to the TUN.
- **TUN devices.**
  - **Linux**: `/dev/net/tun` with `IFF_TUN|IFF_NO_PI`; addresses, MTU and routes by rtnetlink with
    `golang.org/x/sys/unix`, already a dependency.
  - **macOS**: a `utun` interface from a `PF_SYSTEM` control socket, packets behind a 4-byte family;
    addresses by `SIOCAIFADDR` and `SIOCAIFADDR_IN6`, routes by a routing socket.
  - **FreeBSD**: a `/dev/tun` clone with `TUNSIFHEAD`; addresses by ioctl, routes by a routing
    socket.
  - **Windows**: Wintun. `wintun.dll` is loaded at run time with `golang.org/x/sys/windows`, with no
    Go module added; fit's Windows archives carry the signed DLL, which Wintun's licence allows to be
    redistributed unmodified. Addresses and routes by the IP Helper API.
  On the three Unix systems the device's descriptor is read and written on fib's poller (fib
  request A51), so a packet costs no goroutine switch (rule 1). Wintun has no descriptor: its
  receive ring signals an event, so one goroutine per device waits on it and hands packets to a fib
  worker (rule 4's pool of its own, here of one), while sends go into the ring from the worker
  without blocking. Setting addresses and routes can block, and runs on the control plane's bounded
  pool. Opening a device needs `CAP_NET_ADMIN` or root, or Administrator on Windows.
- **Everything is bounded** (rule 11): nodes per network, relay sessions in all and per node, frames
  queued per session (by bytes; past it `DATA` is dropped and counted, never queued, since IP
  tolerates loss), relayed bytes per second per node, routes per node and in the table, and packets
  waiting per peer while its connection opens. Every dial, handshake and session has a timeout, and
  relay sessions are kept alive by `PING` (rule 10).

## Alternatives

- **WireGuard as the tunnel.** It would need `wireguard-go`, which reads its sockets and devices on
  goroutines of its own (rule 1), and its UDP-only transport would still need this relay beside it.
  QUIC is already in fib, and gives path migration, which makes the move from relay to direct free.
- **Relaying IP packets, decrypted, at the server.** Simpler, but the server would see every
  packet; relaying the end-to-end QUIC datagrams costs nothing more and keeps the server blind.
- **TURN over TCP and TLS as the only fallback.** It does pass where only TCP does, but not through
  proxies and firewalls that let only HTTP out; WebSocket and HTTP/2 do.

## What fib needs

- [A50](../fib-api-requests.md#a50-quic-datagram-frames): QUIC DATAGRAM frames, already requested
  for decision 025.
- [A51](../fib-api-requests.md#a51-a-packet-devices-descriptor-on-the-poller): a packet device's
  descriptor read and written on fib's poller, one packet per read and per write.
- F1 of the mesh roadmap, HTTP/2 client CONNECT and extended CONNECT streams (iteration S04), for
  the HTTP/2 transport.
