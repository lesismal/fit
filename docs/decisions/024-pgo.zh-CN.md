# 024：用 cmd/fit/default.pgo 做 profile-guided 构建

[English](024-pgo.md) | [简体中文](024-pgo.zh-CN.md)

状态：已接受（2026-10-26）。

## 背景

2026-10-24 的压测复核里，fit 的 `fixed` 场景在 h2c 上比 M3 的构建（`1486c28`）慢 1.3%：
每秒 373.7–377.1 万对 379–382 万，两边的轮次区间不重叠。当时的怀疑是代码段变大，从 6.14 MB 涨到
8.63 MB，而请求路径并没有改动；这个假说没有成立。去掉几乎所有模块的构建（6.47 MB）反而比完整的慢
0.9%，去掉 provider 的只快 0.6%，而每请求指令数三者几乎相同（13514、13449、13444）。动的是 IPC：
M3 的构建 1.516、main 的 1.504、裁剪版 1.492。

在基准机上采集 profile 的构建，是唯一同时跑赢两者的：比 M3 快 1.8%，比 main 快 3.2%，同样的轮次。

## 决定

- **profile 提交在 `cmd/fit/default.pgo`，94 KB。** `go build` 会自动采用主包目录下的 `default.pgo`
  （`-pgo=auto` 是默认值），所以 `fit` 的每次构建都是有 profile 指导的，包括容器镜像和发布包，不需要额外
  参数。
- **在有测量的地方采集**：基准机上，由 `fit` 服务 `fixed` 与 `site` 两个场景、HTTP/1.1、h2c、h3，负载由
  `bench/` 的发生器施加；三段 9 秒的样本用 `go tool pprof -proto` 合并。它的热点路径就是代理与静态
  handler 走的那条。
- **热路径变化时重新采集**，与测量该变化的那轮基准一起做：过期的 profile 仍然正确，只是收益变小；
  上面的数字是这个 profile 对它采集时的树而言的。

## 测量

基准机上 `bench/ab.sh`，`fixed` 场景、HTTP/1.1、h2c、h3，10 秒一轮、3 轮交替，本分支对合并后的树
（2026-10-26）：**h2c +1.4%**（每秒 382.7 万到 388.0 万，3 轮全部更高）、h3 +3.3%（188.5 万到 194.7 万，
在轮次散布内）、HTTP/1.1 +0.2%（噪声内）。h2c 正是那个比 M3 的构建慢 1.3% 的场景，profile 把它补回来
还有余。

## 影响

- 构建变慢、编译器的内存变高，因为它要按 profile 做优化；本仓库的 CI 构建规模下是几秒的量级。
- 二进制略大：`.text` 从 8.63 MB 到 8.73 MB。
- profile 是仓库里的一个二进制文件。它只有 94 KB，随热路径变化，所以像其他文件一样正常 review，
  不是每台机器都要重新生成的产物。
- 用 `-pgo=off` 构建，是判断某个变化是否由 profile 带来的受支持办法。
