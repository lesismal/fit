# 036：同步：记录、流水线与检查点

[English](036-sync.md) | [简体中文](036-sync.zh-CN.md)

状态：已采纳（2026-11-08），下面的规划决定待审阅。规划见
[开发计划的同步路线](../dev-plan.zh-CN.md#数据同步从生产者到消费者)（I163–I194）；I163 实现其核心。

## 背景

用户希望 fit 把数据从生产者搬到消费者，就像 Filebeat 之于文件、Canal、Debezium 或 DataX 之于数据库：
跟踪文件、跟随 MySQL binlog 或 PostgreSQL 复制槽、一次性复制一张表，并把读到的写入 Elasticsearch、
ClickHouse、Kafka、另一个数据库或 S3。每种基础设施都应既能作源又能作目标，任意两者可以相连，内置连接器
不覆盖的由 WASM 插件补上。这类工具首先看是否丢数据，所以保证先于连接器；I163 只用测试连接器实现这些保证：
记录、流水线、队列、确认和检查点。

## 决定

- **原则，按约束先后。** 不丢数据，并由检查点证明：源的位置只在流水线的每个目标都确认了它之前的每条记录后
  才保存，重启、崩溃或 `kill -9` 都从最后保存的位置继续。事务保持完整：检查点绝不落在源事务内部。一切有界
  （规则 11）：队列按记录数和字节数，批次按记录数、字节数和时间。不占用 fib 的 worker：流水线在自己的
  goroutine 上运行，每条流水线只有少数几个。依赖精简：线协议在 fit 中实现。统一的记录模型。凭据与 fit
  其他地方相同。默认关闭：没有 `sync` 时不建立外连，也不在磁盘上留状态。
- **统一的记录模型。** 每个源产生、每个目标接收的都是 `fitsync.Record`：源与命名空间（`db.table`、索引、
  集合、文件、主题），操作（`insert`、`update`、`delete`、`ddl`、`message`），键，变化前后的行，提交时间，
  事务（ID、首条、末条）和位置。值是有类型的：null、bool、int、uint、float、以文本保存的 decimal、string、
  bytes、time（带偏移）、date、JSON、array 和 map；map 像行保持列序一样保持字段顺序。任何连接器的类型都
  不会泄漏到另一个连接器。
- **能往返所有类型的规范 JSON 形式。** null、布尔值、字符串和数组用 JSON 自身的形式；其他类型都是只含一个
  以类型命名成员的对象：`{"int": -5}`、`{"uint": 5}`、`{"float": 1.5}`（`"NaN"`、`"+Inf"`、`"-Inf"` 写成
  字符串）、`{"decimal": "12.30"}`、`{"bytes": "<base64>"}`、`{"time": "<RFC 3339，纳秒，偏移>"}`、
  `{"date": "2026-11-08"}`、`{"json": <压缩后的文档>}`、`{"map": {...}}`。裸数字被拒绝，因为它的类型只能
  靠猜。记录是由各部分组成的对象，空的部分省略。变换、WASM 插件（I165）、stdout 目标和死信看到的都是这种形式。
- **至少一次，目标幂等。** 崩溃后，最后保存的检查点之后的记录会再写一次；目标按键写入（upsert、文档 ID、
  去重令牌），所以重放会收敛到同一状态。只有目标支持事务时才做到恰好一次（I191）。
- **位置属于源，不透明且是 JSON。** 源在可以从其后继续的记录上设置 `Position`；运行时保存已确认的、结束一个
  事务的最后一个位置（没有事务 ID 的记录自成一个事务），并以 `Run.From` 交还给源。位置必须是 JSON，
  检查点文件才便于阅读和设置（I188）。
- **确认推进由连续位置构成的水位线。** 每条源记录在 `Emit` 时得到一个序号；变换由它产生的记录继承这个序号；
  当每个目标都确认了它变成的每条记录时它才算完成（被丢弃的记录立即完成）。水位线沿队列头部连续完成的记录
  前进，停在其中最后一条结束事务的记录上；因此检查点是所有目标都确认了的最小位置，绝不在事务内部，也绝不越过
  仍欠确认的记录。
- **队列只有一个上限：已读取但尚未被所有目标确认的记录。** `queue.max_records` 和 `queue.max_bytes` 从
  `Emit` 起计算一条记录，直到它在水位线头部被移出；队列满时 `Emit` 等待。因此停滞的目标会让源停下，无论
  各目标的批次里有多少，内存都在上限之内。大于 `max_bytes` 的记录等队列清空后单独通过，所以上限是
  `max_bytes` 与单条记录中较大者。
- **检查点文件。** `<state_dir>/<pipeline>.json`：`{"version": 1, "pipeline", "position", "saved"}`，
  先写到同目录的临时文件，`fsync`，再改名覆盖旧文件，系统允许时再同步目录。位置变化时至多每
  `checkpoint_interval`（5s）写一次，流水线停止时也写；启动时删除崩溃留下的临时文件。版本更高或无法解析的
  文件会阻止流水线启动（它不断重试并说明原因），而不是让它从头开始。
- **检查点保存后才告诉源。** 实现了 `Confirmer` 的源在检查点文件写入后才得到它，而不是水位线一动就得到：
  PostgreSQL 复制槽得知某个 LSN 后会释放之前的 WAL，所以确认一个文件里还没有的位置，崩溃后就会丢数据。
- **失败。** 目标的错误以翻倍的退避重试（`retry`：5 次，200ms 到 30s），从 `BatchError` 指出的那条记录或
  批次开头重试；仍失败的记录，或变换失败的记录，按 `on_error` 处理：`stop` 停止流水线（检查点停在该记录之前），
  `skip` 跳过并记一行日志，`dead_letter` 先写到 `dead_letter` 目标再继续。源失败时整条流水线在同样的退避后
  从检查点重启，只要失败就一直重启；被 stop 的流水线等待配置改变或 fit 重启。
- **连接器和变换是模块。** 命名空间为 `sync.sources`、`sync.sinks` 和 `sync.transforms`；配置用 `module` 和
  `params` 指定一个模块，参数像处理器的一样严格解码，由 `fit validate` 检查（角色的检查会加载每个模块），并在
  schema 和配置参考中描述。I163 提供测试连接器 `generate`、`memory` 和 `stdout`。
- **变换只复制一次记录，delete 保留其键**（I164，与它的计划小节一起待审查）。变换只通过 `Record.Own` 改动记录：
  记录由它之前的变换用 `Clone` 做出时返回它本身，否则返回一个副本，所以源的记录保持读到时的样子，一串变换只复制
  它一次。内置的 `filter`、`route`、`fields`、`key`、`cast`、`mask` 和 `envelope` 从不丢掉记录的键；由之前的变换
  移除的字段构造的 `key` 变换在检查配置时被拒绝，delete 缺少这些字段时保留它已有的键。
- **同步角色。** `sync` 是一个应用角色（决定 028 的注册表）：配置设置了 `sync` 时管理器启动它，之后每份配置
  都应用到它，配置去掉它时停止它。重载比较每条流水线的设置和 `state_dir`，启动新增的、停止删除的、只重启
  设置改变的流水线；停止的流水线先在排空超时内写完手头的记录和检查点。模块加载失败的配置不改变任何东西。
  它的日志是单独的 logger `sync`。
- **协议在 fit 中实现，不用驱动**（下面的规划决定 1）：MySQL、PostgreSQL、MongoDB、Kafka、Redis 和 S3 的
  连接器在 `sync/*/wire` 中实现各自的协议，每个都在 Docker 中对照真实服务器检查。I163 不增加依赖。

## 实现 I163 时做出的决定（待审阅）

1. **包的目录是 `sync`，包名是 `fitsync`。** 规划中的路径（`sync/file`、`sync/mysql/wire`）和配置中的
   `sync` 保持不变，包名也不会遮蔽运行时自己要导入的标准库 `sync`。另一种做法：目录叫 `datasync`。
2. **目标写成 `{"name", "sink": {"module", "params"}, "batch"}`**，模块放在单独的引用中，而不是像规划草图那样
   把 `type` 和目标的设置放在一起，这样 schema、解码器和 `module.Load` 都像对待其他模块引用一样对待它。
   另一种做法：扁平的 `{"name", "type", ...参数, "batch"}`，需要专门的解码器和 schema。
3. **`dead_letter` 是单独的目标**，不是 `sinks` 之一，否则它除了死信还会收到每一条记录。死信是一条 `message`
   记录，其 `after` 包含 `error`、`at`（出错的目标或变换）、`attempts` 和 `record`（原记录的规范 JSON，作为
   JSON 值），并带原记录的命名空间、键和位置。
4. **设置 `sync` 时 `state_dir` 必填**，而不是默认放在 `$XDG_DATA_HOME` 下：检查点放在哪里值得写明，不写就
   不会写任何东西。
5. **重试设置属于流水线**，由它的目标、死信目标和源的重启共用，而不是每个目标各有一份。
6. **批次失败而错误没有指出哪条记录时**，整批重试；次数用完后，把批次的第一条记录当作失败的记录交给
   `on_error`，其余记录以新的次数重试。因此宕机的目标会让每条被跳过的记录都耗尽重试次数，而不是一下子跳过
   整批。
7. **变换接口按记录调用**（`Apply(r, emit)`），在分发 goroutine 上运行；面向 WASM 的批量接口如果基准测试
   需要，由 I165 加入。
8. **源的错误使流水线在退避后重启，只要失败就一直重启**，而目标的错误在用完重试次数后按 `on_error` 处理：
   失去连接的源预计会恢复，为此停止一条流需要人来处理。
9. **配置中的字节数是普通整数**（`max_bytes: 4194304`），与 `rotate` 和媒体库一致，而不是规划草图中的
   `"4MiB"` 这样的字符串。
10. **崩溃测试用钩子，不用子进程。** `Options.Crash` 在几个具名位置（已入队、已分发、已写入、已确认、检查点
    已写临时文件、检查点已保存）被询问，并像 `kill -9` 一样在那里杀掉流水线：之后什么也不保存，检查点的临时
    文件留在原处。以后的连接器测试使用同一个钩子。

## 实现 I165 时做出的决定（待审阅）

计划的 I165 一节列出了全部决定；以下几条改变了上面的记录。

1. **变换可以按批处理。** `BatchTransform` 在 `Apply` 旁加上 `ApplyBatch(in, emit(i, o), fail(i, err))`；分发器把变换
   逐个作用于手上的记录，并像以前一样按源的顺序处理失败。
2. **同步的 WASM ABI** 是 fit 宿主模块旁的 `fit_sync`：导出函数 `fit_sync_transform`、`fit_sync_decode`、
   `fit_sync_encode`、`fit_sync_poll` 和 `fit_sync_write`，各自接收其输入的长度，插件用 `input` 读取输入；结果经
   `record_emit`、`fail`、`output` 和 `checkpoint` 交出；记录用其规范 JSON；配置和日志与请求插件相同。一次调用失败、
   陷入异常或超出时间、内存上限，会使它的记录失败，由 `on_error` 处理；检查点不会越过它们。
3. **连接器插件只能经 `http_request` 与外界通信**，经 fib 的异步客户端，发往其 `allow_hosts` 列出的主机，以及
   `sleep`；变换和编解码器两者都没有。一次轮询的记录是一个整体：轮询返回的检查点放在它的最后一条记录上。
4. **编解码器**是 `sync.codecs` 中实现 `Codec` 的模块；从 I166 起，读写字节的源和目标会使用它。
5. **JSON 在 Go 插件中很慢**：在本机每条 46.5 µs，而内置变换是 81 ns，所以需要规划决定 8 的二进制形式，与压测主机上的
   测量一起放在 I165b。

## 实现 I166 时做出的决定（待审阅）

计划的 I166 一节列出了全部决定；以下几条改变了上面的记录。

1. **内置编解码器。** `line`、`json`（一行数据作为普通 JSON，或整条记录的规范形式）和 `csv` 是 `fitsync` 中
   `sync.codecs` 的模块；连接器在其参数中以模块引用指定一个，不指定时为 `line`。编解码器拒绝的行变成一条保存该行和错误的
   message 记录，既不丢失这一行，也不算源的错误。
2. **文件源的位置**是每个文件的设备号和 inode（在 Windows 上为卷序列号和文件索引）、其开头的指纹、偏移及其记录的键，以及
   最近被截断的文件的开头，使截断前复制出的副本从原文件读到的位置接着读。已关闭且扫描错过 `close_after` 的文件被遗忘，因此它保持有界。源只在
   行与行之间设置位置，每一轮或每 1,000 条记录一次，而不是每条记录都设。
3. **从文件读出的记录有键**：文件的设备号、inode 和首行的哈希，以及偏移，使崩溃后再次读到的行有与先前相同的键，幂等的目标
   会合并这次重放。
4. **文件目标经由日志的文件写入器写出**（决定 034），与进程的日志文件共用：一个路径一个写入器，轮转、保留和压缩与日志相同；
   一个批次在写入并同步之后才确认。

## 实现 I167 时做出的决定（待审阅）

计划的 I167 一节列出了全部决定；以下几条改变了上面的记录。

1. **作业与分块快照。** `mode: "once"` 的流水线是作业。能拆分快照的源实现 `Chunker`：作业开始时 `Chunks` 规划各块（命名空间、
   源自己 JSON 形式的键边界 `lo` 和 `hi`、估计的行数），规划保存在检查点中；`ReadChunk` 读取一块，每次 `job.max_parallel` 块。
   作业的位置记录已完成的块和每个进行中的块所到的位置；一块的最后一条记录携带标记其完成的位置，因此靠水位线，一块只有在每个
   目标都已确认其全部记录后才算完成，被中断的作业不会再读已完成的块。快照记录不带事务。
2. **并行写入者**只用于分块的快照，且只用于实现 `ParallelSink` 的目标：每个有 `job.max_parallel` 个写入者，记录按其键的哈希
   分派，所以一个键绝不会乱序写入；其他情况每个目标一个写入者，如前。
3. **进度保存在检查点中**（`job`：开始与完成时间、读取、写入和失败的记录数、估计的行数、预计剩余时间、已完成的块和规划），
   检查点版本仍为 1。已完成的作业不会在 fit 重启或重载时再次运行；调度的下一个时间点或 `fit sync run` 开始一个新作业，分块的
   源从头开始，其他源从上一个作业结束处开始。
4. **调度**：`job.schedule` 为 cron 的五个字段或描述符，没有秒，按 `job.time_zone`（默认 `UTC`）计，由 fit 自己的解析器
   （`internal/cron`）解析，不增加依赖；运行绝不重叠，错过的时间点不补跑，被中断的作业在启动时立即继续。
5. **`fit sync run <pipeline> [--once]`** 不启动服务器、单独运行一条流水线并以其结果退出：0 全部写入，3 有记录失败，1 停止
   或被中断，2 用法错误；源连续失败超过 `retry.max_attempts` 次即停止，而不是无限重启。

## 实现 I168 时做出的决定（待审阅）

计划的 I168 一节列出了全部决定；以下几条改变了上面的记录。

1. **永久错误。** `fitsync.Permanent(err)` 标记重试也无法解决的错误（被 mapping 拒绝的文档）；目标的写入因它失败时，无论
   单独返回还是作为 `BatchError` 的错误，都立即交给 `on_error`，不经流水线的重试。
2. **目标可以在一次写入内重试。** `elasticsearch` 目标自己重发集群以 429 或 5xx 回应的条目，并带上同一文档后续的写入，使文档
   的最后一次变更仍是最后一次；它的 `BatchError` 指出第一条未写入的记录，运行时从那里起再写这个批次，包括集群在它之后已接受
   的记录，按顺序，每条只确认一次。
3. **429 是背压，不是失败。** 只要它持续就一直等待，占住目标，并经由队列使源停下，且从不计入 `retry.max_attempts`，因此不会
   因为集群繁忙而跳过记录或把记录写入死信。
4. **没有角色引擎的目标自己运行一个**，供 fib 的 HTTP 客户端使用，因此 `fit sync run` 能写入基于 HTTP 的目标。

## 实现 I169 时做出的决定（待审阅）

计划的 I169 一节列出了全部决定；以下几条改变了上面的记录。

1. **Elasticsearch 作为源**（规划决定 6）：先经 point in time 读快照，再按游标字段轮询，只按游标排序（Elasticsearch 8 不按
   `_id` 排序），排除在最后值已读过的 `_id`；位置就是该值和这些 `_id`。流的快照中断后从头开始；检查点越过之后才以不高于它的
   游标值写入的文档会被漏掉，日期游标落后集群时钟 `delay`。删除看不到，但软删除字段（`deleted_field`）会把文档变成删除。
2. **作业的块是经 scroll 读取的 `_id` 切片**，而不是时间点：时间点的切片换一个时间点就不同；中断的块整个重读。有游标的作业
   不分块，所以下次运行只读改动。
3. **`fitsync.ParsePlain`** 按 `json` 编解码器的规则读取普通 JSON 文档，供服务器存放 JSON 的源使用。
## 实现 I187 时做出的决定（待审阅）

计划的 I187 一节列出了全部决定；以下几条改变了上面的记录。

1. **SigV4 由 fit 自己实现**（`syncs3.Signer`），符合上面的原则：fit 和 fib 中都没有可复用的 S3 实现。凭证是访问密钥及由环境
   变量提供的密钥，只读取一次；不读取 AWS 的默认凭证链。
2. **以文件形式写批次的目标，每个批次写一个文件。** `s3` 目标把每个批次写成一个对象（超过 `max_object_bytes` 时写成多个），不跨
   批次保留任何东西，因此对象按目标的 `batch` 上限滚动；跨批次攒行会确认尚未存好的记录。
3. **对象以其第一条记录命名**（提交时间及其位置的哈希），因此同一批次再写一次就是同一个对象、同样的字节；被切成不同批次的重放会
   写出别的对象，与所有目标一样是至少一次。
4. **对象源按键的顺序读取，并能在对象内部继续**：其位置是键和该行之后的偏移；键必须递增，与该目标生成的键一样。
## 实现 I171 时做出的决定（待审阅）

计划的 I171 一节列出了全部决定；以下几条改变了上面的记录。

1. **源可以在检查点之前得知确认。** `fitsync.Acknowledger` 在水位线移动时、检查点保存之前被告知其新位置；`http` 源此时就应答
   客户端，因为所有目标都拿到的东西是安全的；对于服务器在检查点保存前不得释放数据的源，`Confirmer` 仍是对应的钩子。
2. **接收记录的源按其流水线的名字找到。** `fitsync.Run` 带有流水线的名字；`http` 源运行期间以此名字登记，`sync_ingest` 处理器
   据此查找，找不到时回 503。
3. **对于应答客户端的源，`on_error` 处理掉的记录算作已确认**：记录被跳过或送入死信的 HTTP 请求回 200。
4. **HTTP 目标的幂等键**覆盖请求中记录的位置和请求体，因为大多数记录没有位置；重发带同一个键，分批方式不同的重放带另一个键。
## 实现 I170 时做出的决定（待审阅）

计划的 I170 一节列出了全部决定；以下几条改变了上面的记录。

1. **版本来自记录，而不是时钟。** 按版本保留键的最后状态的目标（ClickHouse 的 `ReplacingMergeTree`）从提交时间或行中的
   字段取版本，因为有去重时，重放可能以新令牌再次写入较旧的变更，而后一个批次被丢弃，时钟版本会让较旧的变更胜出。
2. **去重与重放的删除不能并用。** 目标把删除写成语句时（ClickHouse 的轻量 `DELETE`），它的插入不去重：重放的删除会删掉
   去重的插入不会补回的行。
3. **按游标轮询的源按键集分页读取**，`(cursor, key) > (上一行)`，以最后一行的值为位置，因此游标值相同的行各读一次；在作业
   中，它的快照按键的范围分块（`Chunker`）。

## 实现 I172 时做出的决定（待审阅）

计划的 I172 一节列出了全部决定；以下几条改变了上面的记录。

1. **数据库连接是在自己 goroutine 上的阻塞 `net.Conn`**，而不是 fib 的连接：MySQL 客户端（`sync/mysql/wire`）在发出请求的
   goroutine 上按顺序读应答，TLS 用 `crypto/tls`，每次等待受超时限制，每次调用受其 context 限制；基于 HTTP 的系统仍用 fib
   的异步客户端。
2. **配置了到数据库的 TLS 就必须使用，没有 preferred**，并且校验证书；不提供 TLS 的服务端被拒绝，而不是改用明文。
## 实现 I177 时做出的决定（待审阅）

计划的 I177 一节列出了全部决定；以下几条改变了上面的记录。

1. **数据库的 wire 客户端是阻塞连接**，基于 `net.Conn` 与 `crypto/tls`，每个在自己的 goroutine 上，而不是 fib 的异步连接：
   一问一答，COPY 和复制流需要阻塞写的背压，通道绑定需要 `crypto/tls` 看到的服务端证书。基于 HTTP 的系统仍经 fib 出去。
2. **没有静默降级的 `sslmode`**：`disable`、`require`、`verify-ca`、`verify-full`（默认）；通道绑定默认 `prefer`。
## 实现 I186 时做出的决定（待审阅）

计划的 I186 一节列出了全部决定；以下几条改变了上面的记录。

1. **同步有自己的 RESP 客户端**，`sync/redis/wire`（RESP2 与 RESP3、TLS、ACL 用户、pipeline、有上限的应答），而不用
   `tlsmgr/sharedstore` 不导出的 RESP2 客户端；把 `sharedstore` 改用它留待以后。
2. **流的检查点是唯一的游标**：`redis` 源从最后的条目 ID 起用 `XREAD` 读取，不建消费者组，也不在服务器上确认任何东西。
3. **目标可以把服务器对重复的拒绝算作已写入**：以键为条目 ID 时，`redis` 目标把 `XADD` 对不大于流最后 ID 的拒绝视为流已有该
   条目，这让流的复制恰好一次。

## 规划决定（2026-11-08，待审阅）

1. **协议在 fit 中实现，不用驱动。** 另一种做法：在 fit 的接口后面用 go-mysql、pgx、MongoDB 驱动和
   franz-go：眼下省很多工作，但违背设计原则 6。
2. **至少一次，目标幂等；只有目标支持事务时才恰好一次（I191）。**
3. **默认把检查点放在每条流水线的本地文件中**，而不是 `admin.store` 或目标中；一条流水线只在一个 fit 上运行。
4. **每条流水线一个检查点，取最慢的目标。** 另一种做法：每个目标一条流水线。
5. **MySQL 快照不加锁，靠重放收敛**（I175），而不是 DBLog 的水位线算法。
6. **ClickHouse 和 Elasticsearch 作为源时按游标轮询**，看不到删除。
7. **TiDB 的变更经 TiCDC 通过 Kafka 获取**，而不是 TiDB 已弃用的 binlog。
8. **WASM ABI 先用 JSON 传递记录**，只有 I165 的基准测试需要时才用二进制；连接器插件只能使用 HTTP 和定时器，
   不能使用原始套接字。
9. **DDL 只报告，不在 SQL 目标中重放。**
10. **顺序：** 先核心、变换、WASM 和文件，再基于 HTTP 的系统，再数据库，再 Kafka、Redis 和 S3，最后是运维。

## 影响

- 以后的每个连接器都是实现 `Source`、`Sink` 或 `Transform` 的模块，检查点、批次、重试、`on_error`、重载和
  崩溃测试都由运行时提供。
- 目标必须幂等；每个目标的文档说明它如何做到。
- 每条流水线的 goroutine 数量有界：一个监督者、源、分发者、检查点定时器、每个目标一个，以及一个等待各目标的；
  读取分块快照的作业另有 `job.max_parallel` 个读块者，每个 `ParallelSink` 也有同样多的写入者（I167）；`Close` 时全部停止。
