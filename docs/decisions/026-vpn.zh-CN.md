# 026：fit 节点组成的 VPN，能打洞时直连，打不通时经 QUIC、WebSocket 或 HTTP/2 中转

[English](026-vpn.md) | [简体中文](026-vpn.zh-CN.md)

状态：已接受（2026-11-01）。

## 背景

fit 要把多台主机组成一张私有网络：每个节点在 overlay 网络里有一个地址和一块 TUN 网卡，IP 包在节点之间转发，就像在
同一个局域网里，Tailscale 和 ZeroTier 就是这样做的。节点大多在 NAT 后面。两个节点通过在两端 NAT 上打出的洞直接通信
（[决定 025](025-p2p.zh-CN.md) 的 ICE）；打不出洞，或节点配置为不尝试直连时，包经由 server 节点中转。封 UDP、或只放行
HTTPS 的网络很常见，所以中转要能经 QUIC、WebSocket 和 HTTP/2 到达，按配置的顺序尝试，一个失败就退到下一个；节点用哪个
协议也可以在 web 页面上手动指定。

## 决定

- **建在 P2P 里程碑（I84–I93）之上。** 地址发现和打洞用 `p2p/ice` 与 `p2p/stun`；两个节点之间的载荷就是选中的地址对上的
  那条 QUIC 连接，证书指纹经 server 交换，与决定 025 相同。TURN 仍作为 ICE 的 relayed 候选，供放行 UDP 的网络使用；本文
  新增的中转面向不放行 UDP 的网络，是 VPN 的默认中转。
- **包结构。** `vpn/packet`（IP 头和 overlay 路由表）、`vpn/tun`（各系统上的 TUN 设备）、`vpn/relay`（中转协议、中转服务端，
  以及挑选传输协议的客户端）和 `vpn`（节点、协调者和配置里的应用）。
- **IP 包作为 QUIC DATAGRAM 帧**（RFC 9221，fib 请求 A50）走两个节点间的端到端 QUIC 连接：不可靠、无序，丢一个包就像在线路
  上丢了一样，由隧道里的 TCP 去恢复；直连和 QUIC 路径上没有队头阻塞，也没有 TCP 套 TCP 的重传。
- **中转搬运的是端到端 QUIC 连接的包，不是 IP 包。** 对节点来说，中转只是通往某个对端的又一条 `quic.PacketConn` 路径，与 TURN
  allocation 一样：server 按节点 ID 转发不透明的 QUIC 数据报，既读不到也改不了流量（端到端 TLS 1.3）。一对节点一开始就走
  中转，同时进行 ICE 检查，ICE 提名地址对后经 QUIC 的路径迁移切到直连；直连路径的 consent 失效时再切回中转。QUIC 之上
  感知不到这些切换。
- **一种中转协议，三种传输。** 帧是一个类型字节、一个 varint 节点 ID 和载荷：`DATA`（发给所指节点；server 投递时则表示来自
  所指节点）、`GONE`（该节点没有会话）、`PING` 和 `PONG`。源 ID 由 server 按会话已认证的节点填写，节点无法冒充别人。各传输的
  分帧：
  - **QUIC**：一条到 server 的 QUIC 连接；`DATA` 帧作为 DATAGRAM 帧发送，内层 QUIC 不会被重复做成可靠传输；其余帧在一条双向
    流上，带长度前缀。
  - **WebSocket**：每帧一条二进制消息，挂在 server HTTPS 监听的一个可配置路径上（HTTP/1.1 upgrade，客户端支持时用 HTTP/2 上的
    RFC 8441）。
  - **HTTP/2**：一条扩展 CONNECT 流（`:protocol` 为 `fit-relay`），帧在流上带 16 位长度前缀。它需要 fib 的 HTTP/2 客户端
    CONNECT 流，即 [mesh 路线图](../mesh-roadmap.zh-CN.md) 的 F1（迭代 S04）。
  在 WebSocket 和 HTTP/2 上内层 QUIC 仍运行拥塞控制，它看到的是延迟而不是丢包，Tailscale 的 DERP 以及所有 TCP 回退方案都是
  如此。
- **按顺序选择传输，失败回退。** 节点的 `relay.transports` 列出要尝试的传输，默认 `[quic, websocket, http2]`。客户端带连接超时
  （5 秒）拨第一个，失败则拨下一个；会话断开后带退避从头开始。当前不在第一个时，客户端每隔探测间隔（60 秒）探测排在前面的
  传输，切到第一个应答的，先建好新会话再关旧会话，内层 QUIC 连接看到的是路径变化而不是丢失。
- **节点的传输可以手动固定。** `relay.transport` 为 `auto`（按上述顺序）或某一种传输，此时只尝试它，失败则带退避重试并显示为
  失败。它可以在节点配置里设置、在节点自己的 web 页面上设置，或在 server 的 web 页面上为任意节点设置并随该节点的 netmap
  下发；两处都设置时以节点自己的为准，页面会显示当前生效的是哪一处。web 页面就是 fit 的 admin dashboard，修改和其他配置
  一样经 Admin API 及其配置版本。
- **直连可以按节点关闭。** 节点上配置 `p2p: false`，或 server 上为该节点这样配置，就跳过 ICE，其他节点只经中转访问它。
- **协调者就是 server 节点。** 它是一个启用了中转服务端和 I92 信令端点的 fit。节点用 token 加入，从配置的网段（IPv4 和 IPv6）
  分得 overlay 地址，并得到 netmap：每个对端的节点 ID、overlay 地址、它承载的路由、证书指纹，以及上述按节点的设置；有变化
  就重新推送。中转会话用协调者为该节点签发的短期票据认证。
- **路由双向检查。** 从 TUN 读到的包发给前缀包含其目的地址的对端（最长前缀优先）；从对端收到的包只有源地址落在该对端的前缀
  里才写入 TUN，与 WireGuard 的 cryptokey routing 相同。节点可以承载协调者批准的更多前缀（子网路由）。
- **MTU 适配路径。** TUN 的 MTU 默认 1280，即 IPv6 的最小值，在 1500 字节的路径上足以容纳两层 QUIC；可以配置。大于对端
  DATAGRAM 上限的包会被丢弃，并向 TUN 写回 ICMP Fragmentation Needed 或 Packet Too Big。
- **TUN 设备。**
  - **Linux**：`/dev/net/tun`，`IFF_TUN|IFF_NO_PI`；地址、MTU 和路由用 rtnetlink，借助已有依赖 `golang.org/x/sys/unix`。
  - **macOS**：由 `PF_SYSTEM` 控制 socket 创建的 `utun` 接口，包前带 4 字节地址族；地址用 `SIOCAIFADDR` 和
    `SIOCAIFADDR_IN6`，路由用 routing socket。
  - **FreeBSD**：`/dev/tun` 克隆设备，`TUNSIFHEAD`；地址用 ioctl，路由用 routing socket。
  - **Windows**：Wintun。`wintun.dll` 在运行时用 `golang.org/x/sys/windows` 加载，不新增 Go 模块；fit 的 Windows 发布包附带
    签名过的 DLL，Wintun 的许可允许原样再分发。地址和路由用 IP Helper API。
  在三个 Unix 系统上，设备描述符在 fib 的 poller 上读写（fib 请求 A51），每个包不需要 goroutine 切换（规则 1）。Wintun 没有
  描述符：它的接收环通过事件通知，所以每个设备用一个 goroutine 等待该事件并把包交给 fib worker（规则 4 的独立池，这里大小
  为 1），发送则由 worker 直接写入发送环，不会阻塞。设置地址和路由可能阻塞，放在控制面的有界池上执行。打开设备需要
  `CAP_NET_ADMIN` 或 root，Windows 上需要管理员。
- **一切有界**（规则 11）：每个网络的节点数、中转会话总数和每节点数、每个会话排队的帧（按字节；超过后 `DATA` 被丢弃并计数，
  从不排队，因为 IP 容忍丢包）、每节点每秒中转字节数、每节点和全表的路由数，以及对端连接建立期间等待的包。每次拨号、握手
  和会话都有超时，中转会话用 `PING` 保活（规则 10）。

## 其他方案

- **用 WireGuard 作隧道。** 需要 `wireguard-go`，它在自己的 goroutine 上读 socket 和设备（规则 1），而且它只走 UDP，旁边仍需要
  这套中转。QUIC 已经在 fib 里，还带路径迁移，从中转切到直连不需要额外代价。
- **在 server 上解密后中转 IP 包。** 更简单，但 server 会看到每个包；中转端到端 QUIC 数据报不多花成本，server 也看不到内容。
- **只用 TCP 和 TLS 上的 TURN 作回退。** 它能穿过只放行 TCP 的网络，但穿不过只放行 HTTP 的代理和防火墙；WebSocket 和 HTTP/2
  可以。

## 需要 fib 提供的

- [A50](../fib-api-requests.zh-CN.md#a50quic-datagram-帧)：QUIC DATAGRAM 帧，决定 025 已提出。
- [A51](../fib-api-requests.zh-CN.md#a51包设备的描述符在-poller-上读写)：包设备的描述符在 fib 的 poller 上读写，每次读写一个包。
- mesh 路线图的 F1，HTTP/2 客户端 CONNECT 和扩展 CONNECT 流（迭代 S04），用于 HTTP/2 传输。
