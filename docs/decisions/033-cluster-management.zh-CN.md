# 033：集群管理：一个 fit 通过它们已有的 API 管理多个 fit

[English](033-cluster-management.md) | [简体中文](033-cluster-management.zh-CN.md)

状态：其原则、I140、I141 与 I142 已接受（2026-11-06）；I143、I144、I145、I146、I147 与 I149 已实现；标为 *待评审* 的选择在用户裁定之前有效。对应
[开发计划](../dev-plan.zh-CN.md#集群管理)中的 I140–I151。

## 背景

运行多个 fit 的站点——分布在几个地区的边缘、每个服务旁边一个，或每个客户一个——如今只能逐个修改它们的配置：通过各自的
控制台、Admin API 或配置文件。要在所有地方加一条路由、轮换一张证书、摘掉一个上游，就要改同样多次，而且看不到哪些 fit
运行着什么、哪些发生了漂移、一次修改到达了哪些。本方向让一个 fit（管理端）保存其他 fit（成员）的地址和管理员凭据，
把它们一起展示、分组，并一起修改它们的配置：先预览，由每个成员检查，再分阶段推出。

管理端需要成员提供什么，决定了成员要改动多少。每个 fit 都已有 Admin API（bearer 令牌），以及一个凭用户名和密码转发 Admin API
的控制台；每次配置修改都走同一条应用路径，带 ETag 与 `If-Match`，在 `/versions` 留有历史并可回滚。缺少的是：得知一个 fit
是谁、提供什么的途径；不改变任何东西的配置检查；程序可以驱动的登录；以及控制台暴露在网络上后能抵御猜测。

## 决定

本方向的原则，按约束力排序：

- **管理端不在数据路径上。** 无论管理端是否运行，成员都按自己的配置提供服务。成员之间没有共识，也不共享运行时状态。
- **成员的改动尽可能少。** 管理端使用成员的控制台（用户名和密码，之后是会话 cookie 与 CSRF 令牌）或其 Admin API（bearer
  令牌）。成员上的每次修改都走该成员自己的应用路径并带 `If-Match`，记入其 `/versions`，并可在那里回滚。
- **凭据留在管理端的 store 中**，加密保存，在页面中只写入一次、显示时打码；成员的证书经 CA 或固定的 SHA-256 指纹验证。
- **由人来应用。** 对多个成员的修改按成员给出差异，由每个成员试运行检查，经确认后分批应用，带健康闸门与回滚。漂移会被报告，
  点击即可修复；没有无人值守的同步。
- **不阻塞 worker**（[规则 1](../rules.zh-CN.md)）：管理端的调用经 fib 的异步客户端发出，并发有上限，每个调用都有超时，
  每个应答、缓存、历史与审计条目都有上限（[规则 11](../rules.zh-CN.md)）。
- **默认关闭**：没有 `admin.cluster` 就没有集群菜单，也没有任何外发调用。

I140 为每个 fit 增加的内容，使管理端可以管理它：

- **`GET /node`**：在 Admin API 中，以及控制台的 `GET /api/node`（也在 `/api/m/admin/node`）：`id`、`id_kept`、
  `hostname`、`fit_version`、`fib_version`、`go_version`、`os`、`arch`、`started`、`uptime_seconds`、`config_version`、
  `config_etag`、`config_applied`、`config_source`、`roles`（运行中的角色）、`schema_version`、`schema_digest`（二进制生成的
  JSON Schema 的 `sha256:`，摘要相同的两个 fit 接受相同的配置）和 `capabilities`。应答带有运行中配置的 `ETag` 与
  `Fit-Config-Version`。
  - **节点 ID**：配置设置了 `admin.node_id` 时即为它；否则只生成一次随机 UUID，保存在 store 的 `node` 段中，没有 store
    时保存在配置旁的文件里（`fit.json` 旁的 `fit.node-id`，配置目录中的 `fit.node-id`），经临时文件改名写入。有了 store 的
    fit 沿用其文件中的 ID。无处保存时（配置来自标准输入、目录不可写），ID 只持续到 fit 停止，`id_kept` 为 `memory`，fit
    启动时给出警告。`id_kept` 为 `config`、`store`、`file` 或 `memory`。只有设置了 `admin` 的 fit 才生成 ID：没有 `admin`
    的 fit 不提供 `/node`，也不会在配置旁写任何东西。
  - **能力**：管理端在调用某个端点之前检查的名字；名字的含义不变，端点的应答有变化时使用新名字：始终有 `node`、
    `config.if_match`、`config.dry_run`、`config.text`、`config.effective`、`config.check`、`config.versions`、
    `config.transfer`、`status`、`metrics`、`cache`、`logs`、`tokens`、`media`；有 `admin.store` 时有 `store`；
    `admin.console` 运行时有 `console`。
- **试运行。** `PUT`、`PATCH`、`DELETE /config[/<pointer>]`、`POST /load` 与 `PUT /config/text` 接受 `?dry_run=1`（或
  `true`；`0`、`false` 或不带为应用；其他值为 `400`）。请求在同一把锁下走完应用的全部路径：`If-Match`（过期时 `412`）、
  修改、规范化、store 拒绝 `admin`、合并 provider 提供的部分、带引导文件的 `admin` 加载、编译并初始化每个模块，以及像应用时
  绑定那样试绑新监听的地址（普通绑定后立即关闭，`listener.Server.Plan`）。应答与应用时相同：同样的错误、逐字相同、状态码相同；
  或 `200`，带 `"dry_run": true`、运行中的 `version` 与 `etag`、`new_etag`（该配置应用后的 ETag，随后以同样内容应用时即得到
  它）、与运行中配置相同时的 `unchanged`、将新增（地址按书写）与移除的监听，以及应用时会给出的警告（需重启才生效的修改、
  改名的字段），并带 `Fit-Dry-Run: 1`。什么都不变：运行中的配置、其版本、历史、store 与重载计数。控制台把它记为检查，而非应用。
  - 编译时不使用引擎，与 `fit validate` 相同：上游连接池不拨号也不探测。试运行无法得知的：角色自身在应用时的失败（agent 与
    隧道的失败在应用时作为警告报告），以及检查与应用之间对地址的争用。
- **程序可用的登录。** `POST /api/login` 返回 `{"user", "csrf"}` 与会话 cookie，与 `GET /api/session` 相同；程序保存该
  cookie，并在除 GET、HEAD 外的每个请求的 `X-Fit-Csrf` 中发送 `csrf`。被拒绝的登录为 `429`，带 `Retry-After` 与
  `{"error", "retry_after"}`（秒）。
- **按地址与按用户减缓失败的登录。** 一个地址在 15 分钟内失败 5 次后被拒绝 15 分钟，与以前相同；在安静满 15 分钟之前
  每再被锁定一次，时长加倍，最长一小时。一个用户的密码（无论来自哪些地址）连续失败 10 次后，其检查被拒绝 2 秒，此后每再失败
  一次加倍，最长 5 分钟；等待结束后正确的密码可以登录并结束计数，安静 15 分钟也会结束计数。不存在的用户名共用一个计数，因此
  计数表不会比用户多。账户页修改密码时的检查按同样方式计数。
- **页面。** 账户菜单中有 **本节点**：ID（点击复制）、保存位置、主机、版本、启动时间、运行中的配置与角色、schema 摘要与能力。
  配置页面在 **保存并应用** 旁有 **检查**：同一请求带上 `?dry_run=1`，其错误显示在保存错误的位置。

I141 加入的管理端（`admin.cluster`、包 `cluster`、控制台模块 `cluster`；见[集群管理](../cluster.zh-CN.md)）：

- **成员保存在 store 的 `cluster` 节中**，这是一个有自己版本号（1）的文档，保存成员及其凭据，以及后续迭代填写的分组、模板、
  推出和审计日志，在此之前原样保留。更新版本的文档只显示、从不覆盖。
- **访问方式**：控制台的用户名和密码（401 时重新登录；被拒的登录从一分钟退避到 15 分钟；要求修改密码的控制台被报告，其会话登出），
  或 Admin API 的令牌。**TLS**：系统 CA、`ca` PEM 或固定的 `fingerprint`，在握手的 `VerifyConnection` 中检查，被拒的证书
  仍连同其指纹显示；`http` 只用于回环地址。
- **轮询器**是独立的 goroutine，同时最多启动 `max_concurrency` 个轮询；每个轮询是 fib 异步客户端上的一串调用，每个成员一个客户端，
  每次调用受 `timeout` 限制，其应答受 `max_response_bytes` 限制。成员状态记录最近一次轮询的结果（每种失败有各自的类型），以及
  最近一次成功读取到的内容。

I142 加入工作台的**集群**菜单（[其页面](../cluster.zh-CN.md#集群页面)）：

- **概览**：各成员的状态，以卡片或表格显示，按状态着色，可按文本、标签选择器与状态筛选（筛选保存在 URL 中）、排序，并按管理端
  轮询的频率重新读取。
- **节点**：添加、测试、按证书指纹信任、编辑与删除成员，每次修改都带成员 ETag；凭据只写入一次，之后从不回填。
- **成员页**：其状态，以及经管理端以 `GET /api/m/cluster/nodes/<name>/read/<what>` 读取的 `/node`、`/status`、`/versions` 与
  `/config/check`：只转发这四个 GET 的有界转发，使用轮询器的会话。
- `fit run` 检查管理端是否有 store，可以是 `-admin` 在配置旁保存的那个；配置本身不再要求 `admin.store`。

I149 加入的主动连接管理端的 NAT 后成员（[NAT 后面的成员](../cluster.zh-CN.md#nat-后面的成员)）：

- **`admin.cluster.link_address`**：监听引擎上基于 TLS 的 WebSocket 监听，使用只生成一次并保存在文档中的自签名证书，连接数上限为
  `max_nodes` + 16，其中尚未 hello 的至多 32 个。
- **通过注册添加**：访问方式为 `link` 的成员和一个注册令牌（`fite1.`），只保存哈希，带有效期；配置行包含管理端 URL、其证书指纹
  与令牌。成员上的 **`admin.cluster_member`** 经 fib 的 WebSocket 客户端拨出，固定证书，用一次令牌换取自己的凭据（`fitc1.`，
  管理端只保存哈希），保存在其 store 或配置旁，此后用它连接，连接结束后按退避重连。双方用决定 035 的握手证明令牌。
- **经这条连接**，管理端把请求发给成员的 Admin API，由成员在进程内处理（`admin.LinkAPI`）；轮询器、测试、成员页与
  `Manager.Call` 通过同一个传输抽象访问连接型成员，与访问其他成员相同。被删除或重新注册的成员，其连接被吊销，成员忘记凭据。
  文档版本为 2。

I144 加入的分组与对多个成员的操作（[分组与操作](../cluster.zh-CN.md#分组与操作)）：

- **操作**作用于分组的成员或所选成员（`POST /api/m/cluster/ops`，经 `GET ops/<id>` 跟踪）：重新加载、回滚、一致性检查、清除缓存、

- **每个 fit 为此加入**：`POST /reload`（`config.reload`），再次应用运行中的配置；`POST /cache/purge` 接受 `prefixes`

I143 加入的从管理端打开成员自己的页面（[节点切换器](../cluster.zh-CN.md#成员自己的页面节点切换器)）：

I145 加入的模板（[模板](../cluster.zh-CN.md#模板分组共享的配置)）：

- 文档 `templates` 中的**模板**：fit 配置的片段，整体拥有其顶层成员，按名称拥有 `listeners`、`routes`、`services` 与
  `upstreams` 的元素；关联到分组，带 `order`；字符串按成员以 `${node.name}`、`${node.id}`、`${node.hostname}`、

  `GET/POST/PUT/DELETE /api/m/cluster/templates[/<name>]`，以 `from` 从成员的若干部分创建模板。

- **每个 fit 为此加入**：`GET`、`PUT` 与 `DELETE /node/managed`（`node.managed`），即管理端在其上拥有的部分，保存在 store 的
  `managed` 分区中（没有 store 时在内存中），每个部分附带管理端看到其同步之后是否在此被修改；配置页面标出这些部分，并在修改

I146 加入的发布（[发布](../cluster.zh-CN.md#发布分阶段应用的修改)）：

- 文档 `rollouts` 中的**发布**：由模板的修改、同步或从某成员复制的部分规划（`POST /api/m/cluster/rollouts`），取得每个成员的
  期望配置、差异与试运行；以策略（一次全部、滚动、金丝雀）启动，逐批由每个成员带 `If-Match` 的 `PUT /config` 应用，经健康检查，
  检查失败时停止并以 `POST /rollback/{n}` 回滚；可暂停、继续、金丝雀后继续、中止、回滚与放弃；保存每个成员的结果与版本，
  重启时暂停。
- **每个 fit 为此加入**：`GET /status` 应答 `requests`，即 fit 启动以来按状态类别统计、只增不减的已应答请求数
  （`status.requests`），在配置设置了 `metrics` 时提供。

I147 加入的漂移与告警（[漂移与告警](../cluster.zh-CN.md#漂移与告警)）：

- **每次轮询都检查漂移**：成员的一致性检查随轮询获得；关联了模板的成员在配置变化（其 ETag）或同步状态缺失、过旧时，于轮询之后
  与模板比对读取；`GET /api/m/cluster/drift` 列出各成员的漂移，`POST drift/fix` 为所列成员规划一次同步发布
  （`Manager.FixDrift`），只在有人启动后才应用。
- **告警**：规则（成员离线、漂移、发布失败、证书即将到期、上游后端不可用、重新加载失败），各有时长、重复间隔、分组与 Webhook；
  独立的评估器在条件持续达到时长后触发告警并发送，按重复间隔再次发送，条件消失后恢复；静默；Webhook 采用 fit 的 JSON 或聊天服务的
  格式，以其密钥签名，经 fib 的异步客户端发送，每个一次一条，队列有界。规则、Webhook（含 URL 与密钥）、静默以及正在触发与过去的
  告警保存在 store 的 `cluster.alerts` 分区中。`GET/POST/PUT/DELETE /api/m/cluster/alerts/...`。
- **成员**：无需改动；成员照常被读取。

## 待评审

在实现 I140 时做出（2026-11-06）；每一项在用户裁定之前有效。

1. **没有 store 时节点 ID 存放在哪里。** 配置旁的文件，与各角色保存的文件相同；无处持久保存时用 `admin.node_id`。备选：
   用户的状态目录（`$XDG_STATE_HOME`），或没有 store 时不提供 ID。
2. **ID 的形式。** 随机 UUID；`admin.node_id` 接受 1 到 64 个字母、数字、`.`、`_`、`-`。备选：主机名——它随主机改变，
   在容器中还会重复。
3. **试运行的范围。** 所有带请求体或 pointer 的配置写入；不含回滚、reconcile 与导入：它们的配置曾经应用过，或由各自的流程检查。
   备选：全部包含。
4. **试运行会试绑地址。** 普通绑定后立即关闭，使被占用的地址像应用时一样被拒绝。备选：不绑定，被占用的地址到应用时才发现。
5. **按用户减速是拒绝而不是延迟。** 像地址锁定那样回 `429` 并给出等待时间；为延迟而挂住请求会占住登录池。每次猜测最多让
   该用户 5 分钟无法登录；拥有许多地址的攻击者可以一直维持这种状态，而等待结束后正确的密码可以登录。
6. **地址锁定时长加倍。** 第一次仍为 15 分钟，因此一两次输错的代价不比以前大；去而复返的猜测者被减到每小时 5 次。
7. **控制台顶层的 `/api/node`**，与 `/api/m/admin/node` 并存，与计划中的名字一致。

在实现 I141 时做出（2026-11-06）：

8. **成员保存在 store 的一个节中，而不是 payload 的新字段。** 计划要求新增 payload 字段并提升 payload 版本；store 已经保存命名
   的节（格式 3），较旧的 fit 能打开并原样写回，store 的导出也不含节，因此成员的凭据不会随导出离开。新格式会让所有较旧的 fit
   拒绝整个 store，连配置也打不开。该节自带版本号，供自身演进。备选：按计划使用 payload 字段和格式 4。
9. **`admin.cluster` 还需要 `admin.console`**，由它提供端点。备选：同时在 Admin API 中提供（I150 的 CLI 可能需要）。
10. **轮询器是独立的 goroutine**，而不是控制台池中的任务：它只发起异步调用并解析有界的应答，而池中的任务与请求绑定。

## 否决

- **在每个成员上运行代理，或使用自有协议。** 那会在每台主机上多一样要运行、保护和升级的东西；控制台与 Admin API 已经承载了
  管理端需要的一切。
- **成员之间的共识或共享运行时状态**（限流计数、缓存、会话）：这是一个独立的数据面方向，带有管理端设计所避免的故障模式。
- **管理端位于数据路径上**，作为其成员的前端：管理端宕机就会损失流量。
- **跳过编译的试运行**，或经另一个 Configs 的试运行：模块参数只在初始化时检查，而应用的锁、`If-Match` 与 provider 的部分也将不再
  与应用相同。
- **失败后直接锁死用户**：一个猜测者就能把所有管理员挡在外面。
