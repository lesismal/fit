# v1.0.0 report, 2026-10-23

[English](v1.0.0-report-2026-10-23.md) | [简体中文](v1.0.0-report-2026-10-23.zh-CN.md)

Benchmarks for v1.0.0 on the benchmark host. The comparison has grown since M5:

- **Servers**: Envoy runs beside nginx, Caddy, Traefik and fit.
- **Protocols**: four, HTTP/1.1, h2c, h2 (HTTP/2 over TLS) and HTTP/3.
- **CPU and memory**: each run records what the server spent, and works out its efficiency per
  request.
- **fit's goroutines**: counted from its Admin API, once it has started and at most during each run.

This report covers one full run of every server through every scenario and protocol, with idle
connections. Every run had a freshly started server.

In summary:

- **Throughput.**
  - fit leads 10 of the 17 rows: static, the cache but over HTTP/3, and fixed over h2c and h2. It
    answers 1.7 to 6.7 times nginx's rate in them, except static over HTTP/3, a tie (770k against
    764k).
  - nginx leads fixed over HTTP/1.1 (fit −4%) and over HTTP/3 (−13%).
  - nginx also leads proxy over every protocol (fit −5% to −9%), where both are close to what the
    backend can answer.
  - nginx leads cache-hot over HTTP/3 by the widest margin: fit −37%.
  - Envoy is close to nginx on h2c and h2, and ahead of it on fixed there. It is the slowest of all
    over HTTP/3. Caddy and Traefik trail everywhere.
- **CPU per request.**
  - fit spends the least CPU per request on static, cache and fixed over h2c and h2, 1.8 to 10.8 µs.
  - nginx spends less on fixed over HTTP/1.1 and HTTP/3, on proxy (fit 1.2–1.3 times nginx over
    TCP, 2 times over HTTP/3), and on cache-hot over HTTP/3.
  - Caddy and Traefik spend 2 to 7 times what nginx does.
- **Memory.**
  - fit's peak anonymous memory is the lowest in every row but proxy over HTTP/1.1 (Envoy 29 MiB,
    fit 37) and cache-zipf, where fit keeps its 1 GiB cache in memory and nginx keeps its own in
    the page cache.
  - fit answers the most requests a second per MiB in every row but cache-zipf, 1.3 to 32 times
    nginx's figure.
  - nginx's memory grows the least per request in flight on TCP (0.5–14 KiB), from a 198 MiB
    start. fit's grows the least over HTTP/3, but for cache-hot.
- **Idle connections.** fit holds the least memory per idle TLS and WebSocket connection, and is
  second to nginx on plain HTTP/1.1 (1.2 KiB against 0.5).
- **fit's goroutines.** 64 once started; at most 597 under HTTP/1.1 load, 2,329 under h2c
  (cache-hot), 1,787 under h2 and 1,645 under HTTP/3. Idle connections add none.

Results: [`v1.0.0-2026-10-23-linux.json`](v1.0.0-2026-10-23-linux.json). The HTTP/3 runs before and
after the host's UDP buffer limits were raised, [below](#http3-and-the-udp-buffer-limits), are in
[`v1.0.0-2026-10-23-linux-h3-rmem16k.json`](v1.0.0-2026-10-23-linux-h3-rmem16k.json) and

<a id="load-and-connections"></a>
**Load and connections.** Every scenario over a protocol gets the same load, fitbench's defaults,
as the run's JSON records them in `params`:

| Protocol | Load generator | Connections | In flight on each | In flight in all (`in_flight`) |
| --- | --- | ---: | ---: | ---: |
| HTTP/1.1 | wrk, 7 threads (one for each load generator CPU) | 256 | 1 request | 256 |
| h2c | h2load | 64 | 32 streams | 2,048 |
| h2 | h2load | 64 | 32 streams | 2,048 |
| HTTP/3 | h2load built with HTTP/3 | 64 | 32 streams | 2,048 |

| Parameter | Value | |
| --- | ---: | --- |
| `duration` | 30s | each measured run |
| `warmup` | 5s | the same load, unmeasured, just before it |
| `connections` | 256 | wrk's connections |
| `h2_connections`, `h2_streams` | 64, 32 | h2load's connections, and streams on each, for h2c, h2 and HTTP/3 alike |
| `idle_connections` | 10,000 | the connections of each idle kind |
| `idle_settle` | 5s | how long they sit before the server's memory is read |
| `network` | `host` | Docker's host networking, no bridge in between |
| `server_cpus`, `client_cpus`, `backend_cpus` | 0-6, 7-13, 14-15 | the CPUs each side is pinned to |

wrk and h2load keep their connections open for the whole run and send the next request as soon as
an answer comes, so the in-flight count stays at these figures. A proxy's connections to the
backend are its own, up to 4,096 idle ones kept, more than the requests in flight.

**Scenarios.** Each is the same route on every server that can serve it:

| Scenario | Path | Response |
| --- | --- | --- |
| fixed | `/fixed` | 200, `text/plain`, `hello, world`, from the server's config |
| static | `/static/small.html` | a 1 KiB file from disk |
| proxy | `/proxy` | proxied over HTTP/1.1 with keep-alive to the backend (fit answering `hello, world`, on CPUs 14-15) |
| cache-hot | `/cache/hot` | through the server's cache to the cache backend, which answers 4 KiB fresh for 10 minutes: one path, asked again and again |
| cache-zipf | `/cache/1` to `/cache/100000` | the same with 100,000 paths, the n-th most popular asked for as often as 1/n (Zipf's law); HTTP/1.1 only |

Both caches may keep up to 1 GiB: fit's in its memory, nginx's on disk and so in the page cache.
100,000 responses of 4 KiB are about 430 MB, so each keeps every path.

**Idle connections.** `idleconn` opens 10,000 connections of a kind against a freshly started
server, each making one request first, and holds them open, idle:

| Kind | Connection |
| --- | --- |
| http1 | HTTP/1.1 keep-alive on 8080, after a request the server answers 404 |
| tls | the same over TLS 1.3 on 8443 |
| ws | a WebSocket on 8080 at `/ws`, which the server proxies to the WebSocket backend |

**Ports.** Every server serves its routes on four ports, and takes the idle TLS connections on a
fifth:

| Port | Protocol |
| --- | --- |
| 8080 | HTTP/1.1 |
| 8081 | h2c |
| 8445 | h2, over TLS 1.3 by ALPN |
| UDP 8444 | HTTP/3 |
| 8443 | HTTP/1.1 over TLS 1.3, for the idle tls connections |

h2 and HTTP/3 use the harness's self-signed ECDSA P-256 certificate.

**Server configs** ([`configs`](../configs)):

- nginx serves h2 and HTTP/3 from one server block (`listen 8445 ssl` with `http2 on`, and
  `listen 8444 quic`), with 256 streams.
- Caddy runs one site on both ports. Its 8445 allows `h1 h2`, since with `h2` alone it drops TLS
  connections after the client hello. Clients that offer h2 get it by ALPN, and the harness checks
  that they did.
- Traefik has an entry point for each port, with a TLS router for `/proxy`.
- Envoy has a TLS listener with an `HTTP2` connection manager and a QUIC listener with an `HTTP3`
  one, 256 streams each. It runs one worker per CPU it is pinned to (`--cpuset-threads`, 7).
  - Its circuit breakers are raised past what h2load keeps in flight; at their default of 1024 it
    would answer 503.
  - It serves no files and has no cache here, so it runs fixed and proxy only.
- fit has a listener for each port.
- Traefik only proxies. Caddy, Traefik and Envoy have no cache of their own here.

**The HTTP/3 load generator** is h2load built with HTTP/3 on ngtcp2 1.16.0 and nghttp3 1.12.0 over
OpenSSL 3.5 ([`loadgen/Dockerfile.h3`](../loadgen/Dockerfile.h3), Debian trixie). No distribution's
h2load speaks HTTP/3.

**What is measured.** Each measured run has a server started for it, so that the memory and the
goroutines one run leaves behind are not counted in the next.

- **Memory**: the server's anonymous memory (what its processes hold, without page cache) is read
  from the cgroup's files on the host, which costs the server nothing. It is read once the server
  has settled (start), and every 100ms during the warm-up and the run, of which the most is kept
  (peak).
- **CPU**: the cgroup's CPU time over the measured run.
- **Efficiency**, from these:
  - CPU µs per request: the server's CPU time divided by the requests it answered;
  - requests a second per MiB: throughput divided by peak memory;
  - KiB per request in flight: peak less start memory, divided by the requests the load generator
    keeps in flight (256 over HTTP/1.1, 2,048 over the others).
- **Idle memory**: anonymous memory before the idle connections open and after they have sat for
  5s, the difference divided by the connections.
- **Goroutines**: fit's config has an Admin API on 127.0.0.1:9005, off the data path, for counting
  them.

**The host.** `net.core.rmem_max` and `wmem_max` are 7500000 (see
[below](#http3-and-the-udp-buffer-limits)). The `fitconf` kind node (about 5% of one core) and an
idle etcd container stayed up; nothing else ran on the host.

**Errors.** No run had a failed check. nginx had 53 requests "errored" in h2load's terms in fixed
over h2c, and 24 in cache-hot over HTTP/3, out of 18.3 and 14.7 million: requests not finished
when the run stopped. No other run had an error.

## Results by scenario and protocol

One table for each scenario and protocol, with a row for each server, ranked by throughput (TPS),
then CPU efficiency, then memory efficiency. `[↓1]`, `[↓2]` and `[↓3]` mark the three keys, each
highest first; a server ties into the next key only on an equal value. The columns:

| Column | What it is | Better |
| --- | --- | --- |
| **TPS** | requests answered a second over the measured run | higher |
| **CPU EER** | requests per CPU-second: TPS divided by **CPU**, what each core the server kept busy answered. Its inverse is the CPU µs per request | higher |
| **MEM EER** | requests a second for each MiB of **Peak memory**: TPS divided by it | higher |
| **p99** (HTTP/1.1) | wrk's 99th percentile latency | lower |
| **Mean / max** (the others) | h2load's mean and maximum latency; it reports no percentiles | lower |
| **CPU** | the cores the server kept busy: its cgroup's CPU time over the run, divided by the run's length, of the 7 it was pinned to | — |
| **Peak memory** | the most anonymous memory the server held, sampled every 100ms through the warm-up and the run: what its processes allocated (heap, stacks, anonymous mappings), across every process in its container (nginx's master and 7 workers together), without the page cache | lower |
| **KiB/in-flight** | Peak memory less the memory the server held once started and settled, before any load, divided by the requests in flight (256 or 2,048, [above](#load-and-connections)): what load added for each request. For fit on fixed over HTTP/1.1, (20 − 4.9 MiB) / 256 ≈ 60.5 KiB | lower |
| **Hits** (cache scenarios) | the share of requests the server answered without reaching the cache backend, from the backend's own count | higher |
| **Errors** | requests that failed: connect, read or write errors and timeouts (wrk), requests h2load counts as failed, among them those not finished when the run stopped, and any answer other than 2xx | lower |

- Each ranked value is followed by its share of the best in its column, floored, so that only the
  best reads 100%. Each column has its own best: the server with the most TPS need not have the
  most CPU EER.
- **Not run** names the servers that cannot serve the scenario: Traefik only proxies, Envoy serves
  no files, and only nginx and fit have a cache here.
- KiB/in-flight favors a server that allocates up front: nginx starts at 198 MiB, its connection
  tables included, and grows little under load. Read it beside Peak memory. For the Go servers
  much of it is the heap's growth and headroom under load rather than state each request holds.

The tables are rendered from the run's JSON by [`benchreport`](../cmd/benchreport).

### Notes

Once started and settled, before any load, the servers held 198 MiB (nginx, across its master and 7
workers), 11 (Caddy), 17 (Traefik), 15 (Envoy) and 4–5 (fit) of anonymous memory. **KiB/in-flight**
is peak less starting memory, for each request the load generator keeps in flight (256 over
HTTP/1.1, 2,048 over the others): what load adds, which favors a server that allocates up front, as
nginx does.

**Protocols, against each other.**

- h2 costs fit more than it costs nginx. fit answers fixed over h2 at 43% of its h2c rate, and
  static at 58%. nginx answers h2 faster than h2c: 916k against 609k on fixed.
- Envoy's h2 and h2c rates are within 5% of each other.
- Over HTTP/3, nginx answers fixed and static 2.3 and 1.7 times faster than over h2. Envoy is
  slowest of all there.

**Cache hit ratios.** In the cache scenarios both caches answered every request from the cache on
one path. With 100,000 paths, nginx answered 99.85% and fit 99.99%.

Every server kept 6.1–7.0 of its 7 cores busy in every run but nginx and fit on proxy (nginx 3.3–5.5,
fit 5.8–6.3) and nginx on fixed over HTTP/3 (5.5).

On proxy, both wait on the backend, which has 2 CPUs and answers about 260k requests a second. nginx
gets close to that with CPU to spare, so the proxy rows compare CPU per request more than
throughput. For nginx over HTTP/3 on fixed, the limit may be the load generator, or how `reuseport`
spreads 64 QUIC connections over 7 workers.

In cache-zipf, fit holds its 430 MB of cached responses in its own memory, with the Go heap's
headroom on top. nginx holds them on disk, in the page cache, which anonymous memory does not count.
Envoy held 1.4 GiB over HTTP/3 on fixed.

fit's figure over HTTP/1.1 is 60–130 KiB for each of 256 connections, 15–32 MiB in all. That is
likely the Go heap's growth and headroom under load rather than per-connection state, since its idle
connections cost 1.2 KiB each (below).

## HTTP/3 and the UDP buffer limits

Before this report, the host's `net.core.rmem_max` and `wmem_max` were 16384, set at runtime by no
file. They are now 7500000, permanently, in `/etc/sysctl.d/90-fitbench-udp-buffers.conf`. The
HTTP/3 scenarios ran under both, with the harness of the day, which kept one server process for all
of a server's runs. They are in
[`v1.0.0-2026-10-23-linux-h3-rmem16k.json`](v1.0.0-2026-10-23-linux-h3-rmem16k.json) and
[`v1.0.0-2026-10-23-linux-h3-rmem7.5m.json`](v1.0.0-2026-10-23-linux-h3-rmem7.5m.json).

- **Latency.** Caddy and Traefik, whose quic-go asks for 7 MB buffers, had worst-case latencies of
  7.6–15.4 seconds under the old cap. With the raised one they had 74–118ms.
- **Throughput.** Theirs moved by no more than 7%. nginx's proxy rose 10%; the rest moved by 3% or
  less.
- **TCP.** Results are unaffected, since neither the load generators nor the servers size TCP
  buffers past the default.

## What to look at in fit

1. **The cache over HTTP/3.** fit's cache-hot answers 309k against nginx's 490k (−37%), at 22.4 µs
   a request against 14.1 and a maximum latency of 429ms. Over h2c it answers 5.5 times nginx's
   rate. It is the largest gap in this report.
2. **TLS for HTTP/2.** fit's fixed answers 1,639k over h2 against 3,817k over h2c, 2.0 µs a request
   more. nginx is faster over h2 than over h2c.
3. **HTTP/3's fixed response.** fit answers 13% below nginx, at 3.82 µs a request against 2.68.
4. **The proxy's CPU.** fit spends 23.8–27.4 µs a request over TCP against nginx's 18.4–22.6, and
   25.3 over HTTP/3 against 12.5.

All four are worth a profile on the host.
