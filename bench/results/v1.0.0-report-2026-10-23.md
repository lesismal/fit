# v1.0.0 report, 2026-10-23

Benchmarks for v1.0.0 on the benchmark host. The comparison has grown since M5:

- **Servers**: Envoy runs beside nginx, Caddy, Traefik and fit.
- **Protocols**: four, HTTP/1.1, h2c, h2 (HTTP/2 over TLS) and HTTP/3.
- **CPU and memory**: each run records what the server spent, and works out its efficiency per
  request.
- **fit's goroutines**: counted from its Admin API, once it has started and at most during each run.

This report covers one full run of every server through every scenario and protocol, with idle
connections. Every run had a freshly started server.

In summary:

- **Throughput.**
  - fit leads 10 of the 17 rows: static, the cache but over HTTP/3, and fixed over h2c and h2. It
    answers 1.7 to 6.7 times nginx's rate in them, except static over HTTP/3, a tie (770k against
    764k).
  - nginx leads fixed over HTTP/1.1 (fit −4%) and over HTTP/3 (−13%).
  - nginx also leads proxy over every protocol (fit −5% to −9%), where both are close to what the
    backend can answer.
  - nginx leads cache-hot over HTTP/3 by the widest margin: fit −37%.
  - Envoy is close to nginx on h2c and h2, and ahead of it on fixed there. It is the slowest of all
    over HTTP/3. Caddy and Traefik trail everywhere.
- **CPU per request.**
  - fit spends the least CPU per request on static, cache and fixed over h2c and h2, 1.8 to 10.8 µs.
  - nginx spends less on fixed over HTTP/1.1 and HTTP/3, on proxy (fit 1.2–1.3 times nginx over
    TCP, 2 times over HTTP/3), and on cache-hot over HTTP/3.
  - Caddy and Traefik spend 2 to 7 times what nginx does.
- **Memory.**
  - fit's peak anonymous memory is the lowest in every row but proxy over HTTP/1.1 (Envoy 29 MiB,
    fit 37) and cache-zipf, where fit keeps its 1 GiB cache in memory and nginx keeps its own in
    the page cache.
  - fit answers the most requests a second per MiB in every row but cache-zipf, 1.3 to 32 times
    nginx's figure.
  - nginx's memory grows the least per request in flight on TCP (0.5–14 KiB), from a 198 MiB
    start. fit's grows the least over HTTP/3, but for cache-hot.
- **Idle connections.** fit holds the least memory per idle TLS and WebSocket connection, and is
  second to nginx on plain HTTP/1.1 (1.2 KiB against 0.5).
- **fit's goroutines.** 64 once started; at most 597 under HTTP/1.1 load, 2,329 under h2c
  (cache-hot), 1,787 under h2 and 1,645 under HTTP/3. Idle connections add none.

Results: [`v1.0.0-2026-10-23-linux.json`](v1.0.0-2026-10-23-linux.json). The HTTP/3 runs before and
after the host's UDP buffer limits were raised, [below](#http3-and-the-udp-buffer-limits), are in
[`v1.0.0-2026-10-23-linux-h3-rmem16k.json`](v1.0.0-2026-10-23-linux-h3-rmem16k.json) and

**Ports.** Every server serves its routes on four ports:

| Port | Protocol |
| --- | --- |
| 8080 | HTTP/1.1 |
| 8081 | h2c |
| 8445 | h2, over TLS 1.3 by ALPN |
| UDP 8444 | HTTP/3 |

h2 and HTTP/3 use the harness's self-signed ECDSA P-256 certificate.

**Server configs** ([`configs`](../configs)):

- nginx serves h2 and HTTP/3 from one server block (`listen 8445 ssl` with `http2 on`, and
  `listen 8444 quic`), with 256 streams.
- Caddy runs one site on both ports. Its 8445 allows `h1 h2`, since with `h2` alone it drops TLS
  connections after the client hello. Clients that offer h2 get it by ALPN, and the harness checks
  that they did.
- Traefik has an entry point for each port, with a TLS router for `/proxy`.
- Envoy has a TLS listener with an `HTTP2` connection manager and a QUIC listener with an `HTTP3`
  one, 256 streams each. It runs one worker per CPU it is pinned to (`--cpuset-threads`, 7).
  - Its circuit breakers are raised past what h2load keeps in flight; at their default of 1024 it
    would answer 503.
  - It serves no files and has no cache here, so it runs fixed and proxy only.
- fit has a listener for each port.
- Traefik only proxies. Caddy, Traefik and Envoy have no cache of their own here.

**The HTTP/3 load generator** is h2load built with HTTP/3 on ngtcp2 1.16.0 and nghttp3 1.12.0 over
OpenSSL 3.5 ([`loadgen/Dockerfile.h3`](../loadgen/Dockerfile.h3), Debian trixie). No distribution's
h2load speaks HTTP/3.

**What is measured.** Each measured run has a server started for it, so that the memory and the
goroutines one run leaves behind are not counted in the next.

- **Memory**: the server's anonymous memory (what its processes hold, without page cache) is read
  from the cgroup's files on the host, which costs the server nothing. It is read once the server
  has settled (start), and every 100ms during the warm-up and the run, of which the most is kept
  (peak).
- **CPU**: the cgroup's CPU time over the measured run.
- **Efficiency**, from these:
  - CPU µs per request: the server's CPU time divided by the requests it answered;
  - requests a second per MiB: throughput divided by peak memory;
  - KiB per request in flight: peak less start memory, divided by the requests the load generator
    keeps in flight (256 over HTTP/1.1, 2,048 over the others).
- **Goroutines**: fit's config has an Admin API on 127.0.0.1:9005, off the data path, for counting
  them.

**The host.** `net.core.rmem_max` and `wmem_max` are 7500000 (see
[below](#http3-and-the-udp-buffer-limits)). The `fitconf` kind node (about 5% of one core) and an
idle etcd container stayed up; nothing else ran on the host.

**Errors.** No run had a failed check. nginx had 53 requests "errored" in h2load's terms in fixed
over h2c, and 24 in cache-hot over HTTP/3, out of 18.3 and 14.7 million: requests not finished
when the run stopped. No other run had an error.

## HTTP/3 and the UDP buffer limits

Before this report, the host's `net.core.rmem_max` and `wmem_max` were 16384, set at runtime by no
file. They are now 7500000, permanently, in `/etc/sysctl.d/90-fitbench-udp-buffers.conf`. The
HTTP/3 scenarios ran under both, with the harness of the day, which kept one server process for all
of a server's runs. They are in
[`v1.0.0-2026-10-23-linux-h3-rmem16k.json`](v1.0.0-2026-10-23-linux-h3-rmem16k.json) and
[`v1.0.0-2026-10-23-linux-h3-rmem7.5m.json`](v1.0.0-2026-10-23-linux-h3-rmem7.5m.json).

- **Latency.** Caddy and Traefik, whose quic-go asks for 7 MB buffers, had worst-case latencies of
  7.6–15.4 seconds under the old cap. With the raised one they had 74–118ms.
- **Throughput.** Theirs moved by no more than 7%. nginx's proxy rose 10%; the rest moved by 3% or
  less.
- **TCP.** Results are unaffected, since neither the load generators nor the servers size TCP
  buffers past the default.

## What to look at in fit

1. **The cache over HTTP/3.** fit's cache-hot answers 309k against nginx's 490k (−37%), at 22.4 µs
   a request against 14.1 and a maximum latency of 429ms. Over h2c it answers 5.5 times nginx's
   rate. It is the largest gap in this report.
2. **TLS for HTTP/2.** fit's fixed answers 1,639k over h2 against 3,817k over h2c, 2.0 µs a request
   more. nginx is faster over h2 than over h2c.
3. **HTTP/3's fixed response.** fit answers 13% below nginx, at 3.82 µs a request against 2.68.
4. **The proxy's CPU.** fit spends 23.8–27.4 µs a request over TCP against nginx's 18.4–22.6, and
   25.3 over HTTP/3 against 12.5.

All four are worth a profile on the host.
