# v1.0.0 report, 2026-10-23

Benchmarks for v1.0.0 on the benchmark host, with M5's harness settings and two additions: Envoy
beside nginx, Caddy, Traefik and fit, and HTTP/3 beside HTTP/1.1 and h2c. fit's goroutines are now
counted from its Admin API, once it has started and at most during each run under load. This report
covers three runs:

- a full run of every server over HTTP/1.1 and h2c, with idle connections;
- two runs over HTTP/3, one before and one after the host's UDP socket buffer limits were raised.

In summary:

- **HTTP/1.1 and h2c.** fit leads every row but fixed and proxy over HTTP/1.1, where nginx is 5% and
  6% ahead. Envoy is second to fit on h2c (fixed 897k, proxy 233k), and well behind nginx and fit
  over HTTP/1.1.
- **HTTP/3.** nginx leads fixed and proxy, and ties fit on static. With the raised limits nginx
  answers 1,991k fixed (fit 1,749k, −12%) and 288k proxy (fit 240k, −17%); static is 769k against
  fit's 770k. fit is well ahead of Caddy, Traefik and Envoy everywhere: 4.6–5.3 times Caddy and
  Envoy on fixed, 1.8–3.3 times them on proxy.
- **Raising the buffer limits changed HTTP/3 latency, not throughput.** Caddy and Traefik, whose
  quic-go asks for 7 MB buffers, had worst-case latencies of 7.6–15.4 seconds under the old cap;
  with the raised one, 74–118ms. Their throughput moved by no more than 7%. nginx's proxy rose 10%;
  the rest moved by 3% or less.
- **Idle connections.** fit holds the least memory per idle connection of any server but nginx on
  plain HTTP/1.1.
- **fit's goroutines.** fit starts with 64. Under load it reaches 1,685 at most over TCP (proxy over
  HTTP/1.1), and 2,694 and 1,481 over HTTP/3 in the two runs (both proxy). Idle connections add
  none: 64 before 10,000 of them, 62–63 with them.
- **Envoy held 1.4 GB** of anonymous memory under HTTP/3, against 59–112 MB for fit and 280–315 MB
  for nginx.

Results:

- [`envoy-2026-10-23-linux.json`](envoy-2026-10-23-linux.json): every server over HTTP/1.1 and h2c,
  and idle connections at 10k;
- [`h3-2026-10-23-linux-rmem7.5m.json`](h3-2026-10-23-linux-rmem7.5m.json): HTTP/3, with buffer
  limits of 7500000;
- [`h3-2026-10-23-linux.json`](h3-2026-10-23-linux.json): HTTP/3, with the old limits of 16384.

## Setup

| | |
| --- | --- |
| Host | AMD Ryzen 7 7800X3D, 8 cores, 16 threads; 62 GiB; Ubuntu 24.04, Linux 7.0.0-38 |
| Docker | 29.1.3, host networking |
| CPUs | server 0-6, load generators 7-13, backends 14-15 |
| Runs | 30s after a 5s warm-up; wrk with 256 connections; h2load with 64 connections of 32 streams, for h2c and HTTP/3 alike; 10,000 idle connections |
| Servers | nginx 1.31.4, Caddy 2.10.2, Traefik 3.5.0, Envoy 1.40.0 (`envoyproxy/envoy:v1.40.0`), fit at ed5ceb3 on fib v1.6.0, Go 1.27.3 |

- **Envoy**: its config is [`configs/envoy/envoy.yaml`](../configs/envoy/envoy.yaml).
  - One worker per CPU it is pinned to (`--cpuset-threads`, 7).
  - `/fixed` is a `direct_response`, and WebSockets are upgraded at `/ws`. No access log.
  - `/proxy` goes to the backend, with circuit breakers raised past what h2load keeps in flight.
    At their default of 1024, Envoy would answer 503.
  - It serves no files and has no cache here, so it runs fixed and proxy only.
- **HTTP/3 load generator**: h2load 1.68.0 built with HTTP/3 on ngtcp2 1.16.0 and nghttp3 1.12.0
  over OpenSSL 3.5 ([`loadgen/Dockerfile.h3`](../loadgen/Dockerfile.h3), Debian trixie), with 7
  threads. No distribution's h2load speaks HTTP/3: Ubuntu 24.04's, 26.04's and Debian trixie's
  were all built without it. HTTP/1.1 and h2c keep their earlier load generator image.
- **HTTP/3**: TLS 1.3 with the harness's self-signed ECDSA P-256 certificate. Every server serves
  its usual routes on UDP port 8444:
  - nginx uses `listen 8444 quic reuseport` with 256 streams.
  - Caddy runs a site with `protocols h3`.
  - Traefik has an entry point with `http3: {}` and a TLS router for `/proxy`.
  - Envoy has a QUIC listener with an `HTTP3` connection manager, 256 streams and GRO.
  - fit has a listener with `protocols: ["h3"]`.
- **Goroutine count**: fit's config gained an Admin API on 127.0.0.1:9005, off the data path.
- **Buffer limits**: the host's `net.core.rmem_max` and `wmem_max` were 16384, set at runtime by
  no file. They are now 7500000, permanently, in `/etc/sysctl.d/90-fitbench-udp-buffers.conf`.
  - The HTTP/1.1, h2c and idle run and the first HTTP/3 run were made with 16384, the second
    HTTP/3 run with 7500000.
  - TCP results are unaffected: neither wrk nor h2load nor the servers size TCP buffers past the
    default.
- **Other load**: the `fitconf` kind node (about 5% of one core) and an idle etcd container stayed
  up throughout. Nothing else ran on the host.

## HTTP/3

### Throughput, requests per second

No run had an error. In brackets, the change from the run under the old buffer cap.

| Scenario | nginx | caddy | traefik | envoy | fit |
| --- | ---: | ---: | ---: | ---: | ---: |
| fixed | **1,991k** (+3%) | 380k (−4%) | — | 330k (+1%) | 1,749k (−2%) |
| static | 769k (0%) | 159k (0%) | — | — | **770k** (0%) |
| proxy | **288k** (+10%) | 105k (−7%) | 137k (0%) | 72k (−2%) | 240k (−1%) |

Compared with the h2c results above:

- fit answers fixed at 46% of its h2c rate over HTTP/3, static at 31% and proxy at 102%.
- nginx answers fixed and static faster over HTTP/3 than over h2c (3.2 times and 2.1 times).
- Envoy answers fixed and proxy far slower (37% and 31% of h2c).

nginx used only 5.4 of its 7 cores on fixed and 4.2 on proxy. Its fixed rate may be held back by
the load generator, or by how its `reuseport` spreads 64 QUIC connections over 7 workers. Every
other server kept 6.0–7.0 cores busy.

## fit's goroutines

Sampled every 100ms from `go_goroutines`, which includes the Admin API's own few. In each run, one
fit process serves every throughput scenario in turn, so a scenario starts with what the one before
it left.

| When | HTTP/1.1 | h2c | HTTP/3, cap 16384 | HTTP/3, cap 7500000 |
| --- | ---: | ---: | ---: | ---: |
| A second after start, before any load | 64 | 64 | 64 | 64 |
| fixed | 149 | 1,569 | 1,196 | 1,354 |
| static | 1,320 | 1,638 | 1,164 | 921 |
| proxy | **1,685** | 1,412 | **2,694** | **1,481** |

With 10,000 idle connections (http1, tls and ws, a fresh process each), fit had 62, 63 and 62
goroutines, from 63, 64 and 64 before.

The count does not grow with connections: 10,000 idle ones, WebSockets proxied to a backend
included, leave it where it was. Under load it rises with the work fib's workers take on:

- a handful over HTTP/1.1's fixed response;
- about 1,500 with h2c's 2,048 streams in flight;
- up to 2,694 over HTTP/3, varying from run to run.

## What to look at in fit

HTTP/3 is where fit's lead is smallest. fit is behind nginx on fixed (−12%) and proxy (−17%) over
HTTP/3, while over h2c it is 6 times nginx on fixed. Two things are worth a profile on the host:

- fit's fixed rate over HTTP/3 is less than half its h2c rate;
- its goroutines under HTTP/3 proxy reach 1.6 times the TCP peak and vary from run to run.
