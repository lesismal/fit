# 同步基准测试，2026-11-10：第二批场景

[English](report.md) | [简体中文](report.zh-CN.md)

I222 的计划项 S6 到 S9，即 sync 第二批连接器的场景，在基准测试主机上运行（Ryzen 7 7800X3D，8 核 16 线程，
Linux 7.0，Docker 29.1.3），工具与规则同 [2026-11-09 的计划](../sync-2026-11-09/report.zh-CN.md)：每次只跑一个
搬运工具，占用同样的四个物理核，每项 3 轮；每张表及其权重与每行得分见 [tables.md](tables.md)，排名见
[scores.md](scores.md)，各项的 JSON、日志和 fit 的 profile 在旁边。fit 构建于 `6cae0fd0`（分支 `sync2`，
现已在 fit main `1fdb2407` 中，其后的提交不涉及这些路径）。

与 11-09 不同，主机上的 LLM 服务（strata）这次没有停：它空闲（负载 0），但占用 47 GB，而 S1 到 S5 需要的内存
超过剩余的量，所以 **S1 到 S5 没有重跑**：排名中它们的分数是 11-09 的。对比的工具：

| 项 | 场景 | fit 的对手 |
| --- | --- | --- |
| S6 | 文件到 Loki，200 万行 | Promtail 3.5.5 |
| S7 | RabbitMQ（持久的经典队列）到 Kafka，50 万条 | Kafka Connect 加 Apache Camel 的 `spring-rabbitmq-source` 4.14.5 |
| S8 | MQTT（Mosquitto）到 Kafka，50 万条 | Kafka Connect 加 Apache Camel 的 `mqtt5-source` 4.14.5 |
| S9 | SQL Server 2022（CDC）到 Kafka，50 万行 | Debezium 3.0.8 的 SQL Server 连接器 |

## 摘要

- **fit 在每个新项中得分最高**，总排名第一，**98.6**（11-09：98.1），领先 DataX（78.7，仅批量复制）、
  Promtail（70.7，仅 S6）、Filebeat（42.4）、Debezium（38.2，现含 S9）、Canal（29.9）以及
  Kafka Connect 加 Camel（16.3）。
- 与每项的另一个工具相比：
  - **文件到 Loki（S6）**：每秒 27.9 万行，是 Promtail 20.1 万的 1.39 倍，延迟约为其三分之一（p99 464 ms 对
    1,384），内存相当（40 MiB 对 43）；每 CPU 秒多搬 17% 的行。
  - **RabbitMQ 到 Kafka（S7）**：每秒 14 万条，是 Kafka Connect 5 万的 2.8 倍，用 1.34 核对其 1.95 核，
    17 MiB 对其 597 MiB。
  - **MQTT 到 Kafka（S8）**：每秒 10.2 万条，18 MiB。Kafka Connect 的 Camel MQTT 5 源**没有一轮送达全部消息**：
    30 分钟期限到时分别为 50 万中的 499,999、499,995、499,998 条，因此该项得 0 分。
  - **SQL Server 到 Kafka（S9）**：每秒 29.4 万行，是 Debezium 9.1 万的 3.2 倍，用 1.52 核对其 2.47 核，
    51 MiB 对其 1,091 MiB。
- **fit 落后或不完全干净之处：**
  - S9 的延迟：Debezium 的 p99 为 1,518 ms，fit 为 1,597（fit 为其 95%）。两者都按 LSN 轮询 CDC 表，延迟主要
    来自捕获作业的间隔。
  - S9 的重复：第 3 轮中 fit 有 10 行写了两次（目标端 500,010 行，无缺失），期间没有杀进程。Kafka 是至少一次的
    目标，源在快照交接时会重放快照期间写入的行（同 I175）；是否就是这个原因尚未查证。第 1、2 轮完全一致。
  - S7 各轮离散度 fit 为 19%（Kafka Connect 为 29%），原因未查。表中数字为中位数。

## 运行中发现并修复的问题

正式计划前的冒烟测试修复了测试工具：等待循环中以 root 运行的 `rabbitmqctl` 抢在服务器之前创建了 Erlang
cookie，导致 RabbitMQ 启动即退出（现以 `rabbitmq` 用户运行；CI 的互通脚本也有同样的竞争）；Camel 把基准测试的
队列声明为非持久，与驱动程序创建的持久队列冲突（关闭 `autoDeclare`）；中断的运行要等 10 分钟超时才清理；清理
时每个工具每轮遗留 3 到 5 个匿名卷。benchreport 现在按扣除重复后的数量统计缺失：S9 那一行此前显示为
“−10 / 10”。

## 待办

- 停掉 strata，在今天的 fit 上重跑 S1 到 S5，看稳定的记录标识（`Record.Origin`）是否让第一批的路径变慢。
- S9 在没有杀进程时出现的 10 行重复。
- 如有需要，S6、S7、S8 加入更多对手（Vector、Fluent Bit；Benthos/Redpanda Connect）。
