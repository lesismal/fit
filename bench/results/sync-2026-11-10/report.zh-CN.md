# 同步基准测试，2026-11-10：含第二批场景的完整计划

[English](report.md) | [简体中文](report.zh-CN.md)

同步计划的九项在基准测试主机上运行（Ryzen 7 7800X3D，8 核 16 线程，Linux 7.0，Docker 29.1.3），工具与规则同
[2026-11-09 的计划](../sync-2026-11-09/report.zh-CN.md)：每次只跑一个搬运工具，占用同样的四个物理核，每项 3 轮；
每张表及其权重与每行得分见 [tables.md](tables.md)，排名见 [scores.md](scores.md)，各项的 JSON、日志和 fit 的
profile 在旁边。S6 到 S9 是新增的（I222）：sync 第二批连接器的场景。

计划分两次运行：

- **S6 到 S9** 先跑，fit 为 `6cae0fd0`（分支 `sync2`；fit main 之后的提交不涉及这些路径），主机的 LLM 服务
  （strata）没有停，处于空闲；这些场景约需 5 GB。
- **S1 到 S5** 随后重跑，fit 为 main `20482001`，与 11-09 一样，运行期间停掉 strata，结束后再启动。重跑是为了确认
  稳定的记录标识（`Record.Origin`，为第二批的目标所做）没有拖慢第一批的路径：见
  [S1 到 S5 与 11-09 对比](#s1-到-s5-与-11-09-对比)。

新增各项的对手：

| 项 | 场景 | fit 的对手 |
| --- | --- | --- |
| S6 | 文件到 Loki，200 万行 | Promtail 3.5.5 |
| S7 | RabbitMQ（持久的经典队列）到 Kafka，50 万条 | Kafka Connect 加 Apache Camel 的 `spring-rabbitmq-source` 4.14.5 |
| S8 | MQTT（Mosquitto）到 Kafka，50 万条 | Kafka Connect 加 Apache Camel 的 `mqtt5-source` 4.14.5 |
| S9 | SQL Server 2022（CDC）到 Kafka，50 万行 | Debezium 3.0.8 的 SQL Server 连接器 |

## 摘要

- **fit 排名第一，98.8 分**（11-09：仅 S1 到 S5，98.1），并且在每一项中得分最高。其后为 DataX 72.4（仅批量复制）、
  Promtail 70.7（仅 S6）、Filebeat 43.0、Debezium 38.2、Canal 30.4、Kafka Connect 加 Camel 16.3。
- 新增各项与该项另一个工具相比：
  - **文件到 Loki（S6）**：每秒 27.9 万行，是 Promtail 20.1 万的 1.39 倍，延迟约为其三分之一（p99 464 ms 对
    1,384），内存相当（40 MiB 对 43）；每 CPU 秒多搬 17% 的行。
  - **RabbitMQ 到 Kafka（S7）**：每秒 14 万条，是 Kafka Connect 5 万的 2.8 倍，用 1.34 核对其 1.95 核，
    17 MiB 对其 597 MiB。
  - **MQTT 到 Kafka（S8）**：每秒 10.2 万条，18 MiB。Kafka Connect 的 Camel MQTT 5 源**没有一轮送达全部消息**：
    30 分钟期限到时分别为 50 万中的 499,999、499,995、499,998 条，因此该项得 0 分。
  - **SQL Server 到 Kafka（S9）**：每秒 29.4 万行，是 Debezium 9.1 万的 3.2 倍，用 1.52 核对其 2.47 核，
    51 MiB 对其 1,091 MiB。
- **S1 到 S5 保持原样**：S1 到 S4 中 fit 的吞吐与 11-09 相差在 0.7% 以内，CPU 与内存相同；S5 快了 5.8%（DataX
  慢了 6.7%），在批量复制两次运行之间的波动范围内。
- **fit 落后或不完全干净之处：**
  - S5 的 CPU：DataX 每 CPU 秒复制 36.7 万行，fit 33.8 万（92%；11-09 为 86%）。
  - S3 的延迟：Canal 的 p99 为 121 ms，fit 为 299（fit 把记录攒成批，Canal 一次发一个事务；见 11-09）。
  - S9 的延迟：Debezium 的 p99 为 1,518 ms，fit 为 1,597（fit 为其 95%）。两者都按 LSN 轮询 CDC 表，延迟主要
    来自捕获作业的间隔。
  - S9 的重复：第 3 轮中 fit 有 10 行写了两次（目标端 500,010 行，无缺失），期间没有杀进程。Kafka 是至少一次的
    目标，源在快照交接时会重放快照期间写入的行（同 I175）；是否就是这个原因尚未查证。第 1、2 轮完全一致。
  - S7 各轮离散度 fit 为 19%（Kafka Connect 为 29%），原因未查。

## 运行中发现并修复的问题

正式计划前的冒烟测试修复了测试工具：等待循环中以 root 运行的 `rabbitmqctl` 抢在服务器之前创建了 Erlang cookie，
导致 RabbitMQ 启动即退出（现以 `rabbitmq` 用户运行；CI 的互通脚本也有同样的竞争）；Camel 把基准测试的队列声明
为非持久，与驱动程序创建的持久队列冲突（关闭 `autoDeclare`）；中断的运行要等 10 分钟超时才清理；清理时每个工具
每轮遗留 3 到 5 个匿名卷。benchreport 现在按扣除重复后的数量统计缺失：S9 那一行此前显示为“−10 / 10”。
