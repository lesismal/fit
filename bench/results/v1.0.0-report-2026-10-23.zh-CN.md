# v1.0.0 报告，2026-10-23

[English](v1.0.0-report-2026-10-23.md) | [简体中文](v1.0.0-report-2026-10-23.zh-CN.md)

v1.0.0 在压测机上的压测结果。和 M5 相比，对比范围扩大了：

- **服务器**：Envoy 加入，与 nginx、Caddy、Traefik 和 fit 一起比较。
- **协议**：四种，HTTP/1.1、h2c、h2（基于 TLS 的 HTTP/2）和 HTTP/3。
- **CPU 和内存**：每轮都记录服务器的消耗，并算出每个请求的效率。
- **fit 的 goroutine**：从它的 Admin API 统计启动后的数量，以及每轮中的最大值。

本报告是一次完整的运行：每个服务器跑完每个场景和协议，外加空闲连接。每一轮都用新启动的服务器。

概要：

- **吞吐。**
  - 17 行里 fit 领先 10 行：static、除 HTTP/3 外的缓存场景，以及 h2c 和 h2 上的 fixed。这些行里它的
    请求速率是 nginx 的 1.7 到 6.7 倍，只有 HTTP/3 上的 static 是平手（770k 对 764k）。
  - nginx 领先 HTTP/1.1 上的 fixed（fit −4%）和 HTTP/3 上的 fixed（−13%）。
  - nginx 还领先所有协议上的 proxy（fit −5% 到 −9%），两者都已接近后端能应答的上限。
  - nginx 在 HTTP/3 上的 cache-hot 领先幅度最大：fit −37%。
  - Envoy 在 h2c 和 h2 上接近 nginx，fixed 上还超过了它；在 HTTP/3 上它是所有服务器里最慢的。Caddy 和
    Traefik 处处落后。
- **每请求 CPU。**
  - fit 在 static、缓存，以及 h2c 和 h2 上的 fixed 里每请求 CPU 最少，1.8 到 10.8 µs。
  - nginx 在 HTTP/1.1 和 HTTP/3 上的 fixed、proxy（TCP 上 fit 是 nginx 的 1.2–1.3 倍，HTTP/3 上 2 倍）
    以及 HTTP/3 上的 cache-hot 里花得更少。
  - Caddy 和 Traefik 花的是 nginx 的 2 到 7 倍。
- **内存。**
  - 除 HTTP/1.1 上的 proxy（Envoy 29 MiB，fit 37）和 cache-zipf 外，fit 的匿名内存峰值在每一行都最低；
    cache-zipf 里 fit 把 1 GiB 的缓存放在内存里，nginx 则放在页缓存里。
  - 除 cache-zipf 外，fit 每 MiB 内存每秒应答的请求在每一行都最多，是 nginx 的 1.3 到 32 倍。
  - TCP 上 nginx 每个在途请求增加的内存最少（0.5–14 KiB），但它起步就有 198 MiB。HTTP/3 上除 cache-hot
    外，fit 增加得最少。
- **空闲连接。** 每个空闲 TLS 和 WebSocket 连接，fit 占的内存最少；纯 HTTP/1.1 上它仅次于 nginx（1.2 KiB
  对 0.5）。
- **fit 的 goroutine。** 启动后 64 个；HTTP/1.1 负载下最多 597 个，h2c 下 2,329 个（cache-hot），h2 下
  1,787 个，HTTP/3 下 1,645 个。空闲连接不增加 goroutine。

结果：[`v1.0.0-2026-10-23-linux.json`](v1.0.0-2026-10-23-linux.json)。压测机的 UDP 缓冲区上限调高前后的
HTTP/3 运行（见[下文](#http3-and-the-udp-buffer-limits)）在
[`v1.0.0-2026-10-23-linux-h3-rmem16k.json`](v1.0.0-2026-10-23-linux-h3-rmem16k.json) 和

<a id="load-and-connections"></a>
**负载和连接数。** 每个场景在每种协议上的负载都相同，即 fitbench 的默认值，运行的 JSON 在 `params`
里记录了它们：

| 协议 | 压测客户端 | 连接数 | 每连接在途 | 总在途请求（`in_flight`） |
| --- | --- | ---: | ---: | ---: |
| HTTP/1.1 | wrk，7 个线程（压测客户端每个 CPU 一个） | 256 | 1 个请求 | 256 |
| h2c | h2load | 64 | 32 个流 | 2,048 |
| h2 | h2load | 64 | 32 个流 | 2,048 |
| HTTP/3 | 带 HTTP/3 编译的 h2load | 64 | 32 个流 | 2,048 |

| 参数 | 值 | |
| --- | ---: | --- |
| `duration` | 30s | 每轮测量的时长 |
| `warmup` | 5s | 紧接在测量之前、同样的负载，不计入结果 |
| `connections` | 256 | wrk 的连接数 |
| `h2_connections`、`h2_streams` | 64、32 | h2load 的连接数和每连接的流数，h2c、h2 和 HTTP/3 相同 |
| `idle_connections` | 10,000 | 每种空闲连接的数量 |
| `idle_settle` | 5s | 空闲连接放置多久后再读服务器内存 |
| `network` | `host` | Docker 的 host 网络，中间没有 bridge |
| `server_cpus`、`client_cpus`、`backend_cpus` | 0-6、7-13、14-15 | 各方绑定的 CPU |

wrk 和 h2load 在整轮运行中都保持连接打开，一收到应答就发下一个请求，所以在途请求数一直保持在上表的数字。
代理到后端的连接由代理自己管理，最多保留 4,096 个空闲连接，多于在途请求数。

**场景。** 每个场景在能支持它的服务器上都是同一条路由：

| 场景 | 路径 | 应答 |
| --- | --- | --- |
| fixed | `/fixed` | 200，`text/plain`，`hello, world`，由服务器配置直接返回 |
| static | `/static/small.html` | 磁盘上一个 1 KiB 的文件 |
| proxy | `/proxy` | 经 HTTP/1.1 长连接代理到后端（fit 应答 `hello, world`，运行在 CPU 14-15） |
| cache-hot | `/cache/hot` | 经服务器的缓存到缓存后端，后端应答 4 KiB、10 分钟内新鲜：同一个路径反复请求 |
| cache-zipf | `/cache/1` 到 `/cache/100000` | 同上，但有 100,000 个路径，热度第 n 的路径被请求的频率为 1/n（齐普夫定律）；仅 HTTP/1.1 |

两个缓存都最多可存 1 GiB：fit 的在它自己的内存里，nginx 的在磁盘上，因而在页缓存里。100,000 个 4 KiB
的应答约 430 MB，所以两者都能存下每个路径。

**空闲连接。** `idleconn` 对一台新启动的服务器打开 10,000 个某种类型的连接，每个连接先发一个请求，然后
保持打开、空闲：

| 类型 | 连接 |
| --- | --- |
| http1 | 8080 上的 HTTP/1.1 长连接，先发一个服务器应答 404 的请求 |
| tls | 同上，但在 8443 上走 TLS 1.3 |
| ws | 8080 上 `/ws` 的 WebSocket，服务器把它代理到 WebSocket 后端 |

**端口。** 每个服务器在四个端口上提供路由，另在第五个端口上接受空闲 TLS 连接：

| 端口 | 协议 |
| --- | --- |
| 8080 | HTTP/1.1 |
| 8081 | h2c |
| 8445 | h2，基于 TLS 1.3，经 ALPN 协商 |
| UDP 8444 | HTTP/3 |
| 8443 | 基于 TLS 1.3 的 HTTP/1.1，供空闲 tls 连接使用 |

h2 和 HTTP/3 使用压测工具自签名的 ECDSA P-256 证书。

**服务器配置**（[`configs`](../configs)）：

- nginx 在一个 server 块里提供 h2 和 HTTP/3（`listen 8445 ssl` 加 `http2 on`，以及 `listen 8444 quic`），
  256 个流。
- Caddy 在两个端口上运行同一个站点。它的 8445 允许 `h1 h2`，因为只配 `h2` 时它会在 client hello 后断开
  TLS 连接。提供 h2 的客户端经 ALPN 拿到 h2，压测工具会检查确实如此。
- Traefik 每个端口一个 entry point，`/proxy` 有一个 TLS 路由。
- Envoy 有一个带 `HTTP2` 连接管理器的 TLS 监听器和一个带 `HTTP3` 连接管理器的 QUIC 监听器，各 256 个流。
  它为绑定的每个 CPU 运行一个 worker（`--cpuset-threads`，7 个）。
  - 它的熔断阈值调到了 h2load 在途请求数之上；按默认的 1024，它会应答 503。
  - 这里它不提供文件、也没有缓存，所以只跑 fixed 和 proxy。
- fit 每个端口一个监听器。
- Traefik 只做代理。Caddy、Traefik 和 Envoy 在这里没有自己的缓存。

**HTTP/3 压测客户端** 是基于 ngtcp2 1.16.0 和 nghttp3 1.12.0、OpenSSL 3.5 编译的带 HTTP/3 的 h2load
（[`loadgen/Dockerfile.h3`](../loadgen/Dockerfile.h3)，Debian trixie）。没有哪个发行版的 h2load 支持 HTTP/3。

**测量内容。** 每轮测量都单独启动一个服务器，这样上一轮留下的内存和 goroutine 不会算进下一轮。

- **内存**：服务器的匿名内存（其进程持有的内存，不含页缓存），从主机上的 cgroup 文件读取，不占服务器任何
  开销。服务器稳定后读一次（起始），预热和测量期间每 100ms 读一次，保留其中的最大值（峰值）。
- **CPU**：测量期间 cgroup 的 CPU 时间。
- **效率**，由以上数据算出：
  - 每请求 CPU µs：服务器的 CPU 时间除以它应答的请求数；
  - 每 MiB 每秒请求数：吞吐除以内存峰值；
  - 每在途请求 KiB：峰值减起始内存，除以压测客户端保持的在途请求数（HTTP/1.1 为 256，其他为 2,048）。
- **空闲内存**：空闲连接打开前和放置 5s 后的匿名内存之差，除以连接数。
- **Goroutine**：fit 的配置在 127.0.0.1:9005 上开了 Admin API（不在数据路径上），用于统计。

**主机。** `net.core.rmem_max` 和 `wmem_max` 为 7500000（见[下文](#http3-and-the-udp-buffer-limits)）。
`fitconf` 的 kind 节点（约占一个核的 5%）和一个空闲的 etcd 容器一直在运行；主机上没有其他负载。

**错误。** 没有一轮的检查失败。nginx 在 h2c 上的 fixed 有 53 个请求被 h2load 计为 "errored"，HTTP/3 上的
cache-hot 有 24 个，分别出自 1,830 万和 1,470 万个请求：都是运行停止时尚未完成的请求。其他各轮都没有错误。

## 按场景和协议的结果

每个场景和协议一张表，每个服务器一行，按吞吐（TPS）排序，其次是 CPU 效率，再次是内存效率。`[↓1]`、
`[↓2]` 和 `[↓3]` 标出这三个排序键，都是从高到低；只有前一个键的值相等时，才由下一个键决定先后。各列：

| 列 | 含义 | 更好 |
| --- | --- | --- |
| **TPS** | 测量期间每秒应答的请求数 | 越高越好 |
| **CPU EER** | 每 CPU 秒的请求数：TPS 除以 **CPU**，即服务器每占满一个核能应答多少请求。它的倒数就是每请求的 CPU µs | 越高越好 |
| **MEM EER** | **Peak memory** 每 MiB 每秒的请求数：TPS 除以内存峰值 | 越高越好 |
| **p99**（HTTP/1.1） | wrk 的 99 分位延迟 | 越低越好 |
| **Mean / max**（其他协议） | h2load 的平均和最大延迟；它不报告分位数 | 越低越好 |
| **CPU** | 服务器占满的核数：测量期间 cgroup 的 CPU 时间除以测量时长，最多为它绑定的 7 个 | — |
| **Peak memory** | 服务器匿名内存的最大值，在预热和测量期间每 100ms 采样一次：其进程分配的内存（堆、栈、匿名映射），容器里所有进程合计（nginx 的 master 和 7 个 worker 一起算），不含页缓存 | 越低越好 |
| **KiB/in-flight** | 内存峰值减去服务器启动并稳定后、加负载前的内存，再除以在途请求数（256 或 2,048，见[上文](#load-and-connections)）：负载给每个请求带来的额外内存。例如 fit 在 HTTP/1.1 上的 fixed：(20 − 4.9 MiB) / 256 ≈ 60.5 KiB | 越低越好 |
| **Hits**（缓存场景） | 服务器不经缓存后端就应答的请求占比，按后端自己的计数算出 | 越高越好 |
| **Errors** | 失败的请求：连接、读、写错误和超时（wrk），h2load 计为失败的请求（包括运行停止时尚未完成的），以及任何非 2xx 的应答 | 越低越好 |

- 每个参与排序的值后面跟着它占该列最优值的百分比，向下取整，所以只有最优值显示 100%。每列有各自的最优值：
  TPS 最高的服务器不一定 CPU EER 也最高。
- 表下的 **未运行** 列出不支持该场景的服务器：Traefik 只做代理，Envoy 不提供文件，这里只有 nginx 和 fit
  有缓存。
- KiB/in-flight 对启动时就预先分配内存的服务器有利：nginx 起步就是 198 MiB（包括它的连接表），负载下几乎
  不再增长。看这一列时要和 Peak memory 一起看。对 Go 写的服务器，其中大部分是负载下堆的增长和 GC 留出的
  余量，而不是每个请求真正持有的状态。

这些表由 [`benchreport`](../cmd/benchreport) 从运行的 JSON 生成，表头保留英文。

### 说明

服务器启动并稳定后、加负载前，持有的匿名内存为：nginx 198 MiB（master 和 7 个 worker 合计）、Caddy 11、
Traefik 17、Envoy 15、fit 4–5。**KiB/in-flight** 是峰值减起始内存，摊到压测客户端保持的每个在途请求上
（HTTP/1.1 为 256，其他为 2,048）：即负载带来的增量，这对像 nginx 那样预先分配内存的服务器有利。

**协议之间的比较。**

- h2 给 fit 带来的开销比给 nginx 的大。fit 在 h2 上的 fixed 只有它 h2c 速率的 43%，static 为 58%。nginx 的
  h2 反而比 h2c 快：fixed 上 916k 对 609k。
- Envoy 的 h2 和 h2c 速率相差不到 5%。
- 在 HTTP/3 上，nginx 的 fixed 和 static 比 h2 上快 2.3 倍和 1.7 倍。Envoy 在这里最慢。

**缓存命中率。** 单路径的缓存场景里，两个缓存都从缓存应答了每个请求。100,000 个路径时，nginx 命中 99.85%，
fit 命中 99.99%。

除 proxy 上的 nginx 和 fit（nginx 3.3–5.5，fit 5.8–6.3）以及 HTTP/3 上 fixed 的 nginx（5.5）外，每个服务器
在每一轮都占满了 7 个核中的 6.1–7.0 个。

在 proxy 上，两者都在等后端，后端有 2 个 CPU，每秒约能应答 260k 个请求。nginx 在还有 CPU 余量的情况下就接近
了这个上限，所以 proxy 这几行比的更多是每请求 CPU，而不是吞吐。nginx 在 HTTP/3 上的 fixed，瓶颈可能在压测
客户端，或者在 `reuseport` 把 64 个 QUIC 连接分到 7 个 worker 上的方式。

在 cache-zipf 里，fit 把 430 MB 的缓存应答放在自己的内存里，上面还有 Go 堆的余量。nginx 把它们放在磁盘上，
即页缓存里，匿名内存不计这部分。Envoy 在 HTTP/3 上的 fixed 用了 1.4 GiB。

fit 在 HTTP/1.1 上的这项数字是 256 个连接每个 60–130 KiB，合计 15–32 MiB。这很可能是负载下 Go 堆的增长和
余量，而不是每个连接的状态，因为它每个空闲连接只占 1.2 KiB（见下文）。

<a id="fits-goroutines"></a>
## fit 的 goroutine

每 100ms 从 `go_goroutines` 采样一次，其中包括 Admin API 自己的几个。每轮都从新启动的 fit 开始，那时有
63–64 个。

| 场景 | HTTP/1.1 | h2c | h2 | HTTP/3 |
| --- | ---: | ---: | ---: | ---: |
| fixed | 164 | 1,662 | 968 | 1,079 |
| static | 156 | 1,762 | 1,466 | 1,003 |
| proxy | 597 | 2,200 | 1,230 | 1,113 |
| cache-hot | 393 | **2,329** | 1,787 | 1,645 |
| cache-zipf | 379 | — | — | — |

持有 10,000 个空闲连接时（http1、tls 和 ws，每种一台新服务器），fit 的 goroutine 为 62、63 和 62 个，打开
前为 64、63 和 63 个。

goroutine 数不随连接数增长。负载下它随 fib 的 worker 承接的工作而上升：

- HTTP/1.1 的 256 个连接下，几百个；
- h2c、h2 和 HTTP/3 的 2,048 个在途流下，1,000 到 2,300 个。

它始终低于 2,400。

<a id="http3-and-the-udp-buffer-limits"></a>
## HTTP/3 和 UDP 缓冲区上限

本报告之前，压测机的 `net.core.rmem_max` 和 `wmem_max` 为 16384，是运行时设置的，没有对应的配置文件。现在
它们永久设为 7500000，写在 `/etc/sysctl.d/90-fitbench-udp-buffers.conf`。HTTP/3 场景在两种设置下都跑过，
用的是当时的压测工具，它让一个服务器的所有轮次共用一个服务器进程。结果在
[`v1.0.0-2026-10-23-linux-h3-rmem16k.json`](v1.0.0-2026-10-23-linux-h3-rmem16k.json) 和
[`v1.0.0-2026-10-23-linux-h3-rmem7.5m.json`](v1.0.0-2026-10-23-linux-h3-rmem7.5m.json)。

- **延迟。** Caddy 和 Traefik 的 quic-go 会申请 7 MB 的缓冲区，在旧上限下最坏延迟达 7.6–15.4 秒；上限调高
  后为 74–118ms。
- **吞吐。** 它们的吞吐变化不超过 7%。nginx 的 proxy 提高了 10%；其余变化在 3% 以内。
- **TCP。** 结果不受影响，因为压测客户端和服务器都不会把 TCP 缓冲区设到默认值以上。

## fit 值得关注的地方

1. **HTTP/3 上的缓存。** fit 的 cache-hot 应答 309k，nginx 为 490k（−37%），每请求 22.4 µs 对 14.1，最大
   延迟 429ms。在 h2c 上它的速率是 nginx 的 5.5 倍。这是本报告里最大的差距。
2. **HTTP/2 的 TLS。** fit 的 fixed 在 h2 上应答 1,639k，在 h2c 上 3,817k，每请求多 2.0 µs。nginx 的 h2 反而
   比 h2c 快。
3. **HTTP/3 的 fixed。** fit 比 nginx 低 13%，每请求 3.82 µs 对 2.68。
4. **代理的 CPU。** fit 在 TCP 上每请求花 23.8–27.4 µs，nginx 为 18.4–22.6；HTTP/3 上为 25.3 对 12.5。

这四项都值得在压测机上做一次性能剖析。
