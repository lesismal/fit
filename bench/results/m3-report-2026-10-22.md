# M3 report, 2026-10-22

Benchmarks at the end of M3 (gateway features, I36–I55), on the same Linux host and with the same
harness settings as the [M1](m1-report-2026-10-19.md) and [M2](m2-report-2026-10-20.md) reports,
with fit at commit 1486c28 and fib's `main` at 4f1c3e9. M3's exit tests are functional (I55,
`make m3-exit`); this report is the full harness that rule 21 asks for at a milestone's end, and
the middleware's micro-benchmarks.

- fit still meets every M1 target in the [roadmap](../../docs/roadmap.md#performance-targets).
- The proxy is faster than at M2: 248k requests a second over HTTP/1.1, 94% of nginx (86% at M2),
  with its p99 down from 3.6 ms to 2.4 ms and its CPU per request from 26.8 µs to 23.4 µs; over
  h2c, 241k, 95% (94%). This report did not profile it; the likely source is the fib changes
  since M2 on the HTTP/1 client's path (A20's own request writer and response reader, A22's idle
  clock), since the rest of M3 adds nothing to the proxy's path unless a config asks for it.
- fit proxies WebSockets since I47: an idle one costs it 5.5 KiB, against nginx's 17.8, Caddy's
  95.8 and Traefik's 117.7.
- Fixed responses and static files are within 1.3% of M2.

## Results by scenario and protocol

One table for each scenario and protocol, with a row for each server, ranked by throughput (TPS),
then CPU efficiency, then memory efficiency:

- **TPS**: requests a second.
- **CPU EER**: requests per CPU-second, throughput for each core the server kept busy.
- **MEM EER**: requests a second for each MiB of the server's anonymous memory,
  at the end of the run.
- Each ranked value is followed by its share of the best in its column, floored, so that only the
  best reads 100%.
- **Latency**: wrk's p99 over HTTP/1.1, and h2load's mean and maximum otherwise, since it reports
  no percentiles.
- **CPU**: the cores the server kept busy, of the 7 it was pinned to.

The tables are rendered from the run's JSON by [`benchreport`](../cmd/benchreport).

### Notes

nginx, Caddy and Traefik are within 2% of their M2 numbers, so the host and the load generators
measure as they did. wrk on seven CPUs still holds fit's fixed and static responses over HTTP/1.1
near 780k.

fit's p50 over HTTP/1.1 is close to nginx's or below it (fixed 0.17 ms against 0.16, static 0.16
against 0.53, proxy 0.99 against 0.96); its tail is still behind: p99.9 3.9, 3.2 and 4.8 ms against
nginx's 1.9, 0.9 and 2.0.

## The modules

`BenchmarkModule` (I55) serves a request through each middleware in front of a handler that
answers at once, and through each handler, in process, without a network: what one adds to a
request on the worker. ns and allocations per request, the median of five runs.

| Module | ns | B | allocs |
| --- | ---: | ---: | ---: |
| `rewrite` | 462 | 2,704 | 6 |
| `redirect` | 347 | 1,072 | 8 |
| `headers` | 879 | 3,552 | 14 |
| `rate_limit` | 630 | 2,704 | 6 |
| `concurrency_limit` | 648 | 3,200 | 13 |
| `body_limit` | 448 | 2,704 | 6 |
| `basic_auth` | 843 | 2,912 | 11 |
| `client_cert` | 457 | 2,704 | 6 |
| `forward_auth` | 29,956 | 5,873 | 64 |
| `jwt` | 962 | 3,024 | 10 |
| `circuit_breaker` | 965 | 3,648 | 16 |
| `compress` | 2,953 | 2,135 | 26 |
| `proxy` | 30,093 | 5,511 | 53 |
| `static` | 1,105 | 8,896 | 6 |
| `respond` | 265 | 664 | 6 |
| `test_late` | 429 | 2,704 | 6 |

The handler behind each middleware is `respond` with a 2,000-byte body, which is what the
`test_late` row measures alone (in the benchmark it answers at once): 430 ns and 2,704 bytes, most
of them the test recorder's copy of the response. What a middleware adds is its row less that one:
from nothing (`client_cert` without a certificate, `body_limit` on a GET) to 0.5 µs (`jwt`,
`circuit_breaker`, `headers`) and 2.5 µs (`compress`, gzip of the 2,000 bytes). `basic_auth`'s
row is a password already checked, remembered as a keyed SHA-256; the first check of a password
is bcrypt's, on its own pool. `forward_auth` and `proxy` include a request over loopback to a
local net/http server, which is most of their 30 µs. `static` serves a cached file.

The I55 test beside these, `TestNoModuleBlocks`, is what checks that none of them waits on the
worker.
