- **API 网关走 HTTP/1.1 又快了 7-9%：** W1 每一档 +7.3% 到 +9.0%（并发 500 每秒 263,684，每请求 22.57 µs，之前 24.49），

- **fit 没有任何一项变慢。** 58 轮中 13 轮比第一次快 3% 以上；唯一低于 -3% 的 W4 HTTP/1.1 下载（-3.2%）在 3 轮 A/B 中为

## 改了什么

fib 从 3664a1e 到 c3f2c70：

Content-Length、Host 和客户端自带的转发字段，追加转发字段和 Traceparent；受信任的客户端、Expect、Trailer、gRPC 和镜像仍走

## W6 的停顿：来自压测客户端

在压测客户端容器中，h2load 把逐请求日志写到 ext4 之上的 overlayfs。ext4 每 5 秒提交一次日志，大约每次提交都有一个 h2load
线程的写入为一个正在 I/O 的缓冲等待约 10 ms，其他线程排队等文件位置锁：既不发请求也不读响应。慢请求成批出现，间隔正好
5.000 或 10.01 秒；fit 的 runtime trace 显示在这些时刻它的 loop 在 netpoll 中无事可读地停了 8.7 ms（没有超过 186 µs 的
GC 停顿）；tcpdump 显示这期间完全没有流量；bpftrace 抓到 h2load 线程在 ext4 日志下的 `io_schedule` 和 `fdget_pos` 上；
同一工具下的 nginx 也有同样的停顿。fit 46259c0 在压测客户端的 `/tmp` 上挂载 tmpfs。

| W6 每秒 30,000 | p99.9 第一次 → 本次（ms） | 最大值（ms） |
| --- | --- | --- |
| fit，h2 | 6.17 → **1.83** | 11.06 → **2.78** |
| fit，HTTP/1.1 | 10.67 → 3.13 | 12.54 → 5.14 |
| nginx，h2 | 2.73 → 2.14 | 10.88 → 2.59 |
| nginx，HTTP/1.1 | 3.32 → 1.89 | 11.70 → 3.05 |
| Envoy，h2 | 10.87 → 4.55 | 12.93 → 5.24 |

在每秒 200,000 时 fit 的尾延迟仍高于 nginx（p99 4.9-5.1 ms 对 3.1-4.2，最大 16-20 ms 对 8），这是剩下的一项延迟问题。

## 内存：等锁的 worker

并发 5,000 时 fit 有 7,700-8,900 个 goroutine：约 3,400 个 worker 停在 fib HTTP 客户端的锁上（连接收到数据时的
`Client.release`、发送时的 `Client.enqueue`），每个都处在一次读取中，持有 16 KiB 读缓冲和一个发送缓冲，占上次 GC 时
160 MB 存活堆中的 95 MB，其余是空闲 worker。fib 默认允许池增长到每 CPU 1,000 个 worker，每个发现其他 worker 都忙的任务
都会启动一个新的，于是锁竞争变成了数千个持有缓冲的 goroutine。fit 现在把每个引擎限制为每 CPU 100 个（af047ce）；超出的
任务在池的队列中等待，不持有任何东西。并发 5,000 的 A/B：HTTP/1.1 361-392 → 200-221 MiB，h2 378-403 → 239-258，
goroutine 约 8,000 → 1,280-2,000，吞吐在噪声内。锁本身仍有竞争。

## 剩下的

- **W1 HTTP/1.1 为 nginx 的 83-91%：** 并发 500 时每请求差 3 µs。高并发下 fib HTTP 客户端的锁仍有竞争（现在受 worker
  上限约束，不再以内存为代价）；下一步是把每个主机的空闲与等待列表分片，或让阻塞的操作交给持锁者执行。
- **W6 每秒 200,000：** fit 的 p99 和最大值高于 nginx。
- **网站走 HTTP/3 为 nginx 的 53-87%**，是按字节的 AES-GCM（Go 1.27 的 amd64 GCM 没有 VAES 路径）和带 GSO 的 UDP 发送。
