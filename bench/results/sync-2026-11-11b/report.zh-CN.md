# 同步基准测试，2026-11-11（第二次运行）：记录与 Loki 优化之后

[English](report.md) | [简体中文](report.zh-CN.md)

再次运行完整计划，fit 为 `28ce0b65`（fib `aabd7c2`），主机、工具、规则与权重同
[11-11 第一次运行](../sync-2026-11-11/report.zh-CN.md)。第一次运行发现 fit 每条记录的 CPU 比 11-10 多 8% 到 20%，
且 S6 落后于 Alloy。两次运行之间 fit 有两处改动（见 dev-plan 中 I219 与 I222 的说明）：

- **一条记录重新回到 504 字节。** 自 11-10 起给每条记录加上的流水线名和世代，使 `sync.Record` 从 504 字节涨到
  536 字节，超过 512：超过这个大小，Go 的分配器不再按 span 整体标记对象，垃圾回收要逐个扫描。现在它们放在每次
  运行一个的结构里，记录只持有一个指针。emit 路径也不再为每条记录读时钟。流水线基准：每条记录从 505 ns 回到
  426 ns（11-10：427）。
- **Loki 目标与文件源几乎不再分配内存。** 目标此前为每行的每个标签值都新建一个 `strings.Replacer`（占 CPU 的
  17%，分配字节的 68%）：现在无需转义的值直接使用，同一流的连续记录复用其标签，行、流、protobuf 正文与 snappy
  输出都编码进池化的缓冲区。文件源用一次分配构造一行的记录。

每张表及其权重与得分见 [tables.md](tables.md)，排名见 [scores.md](scores.md)。运行期间 strata 和一个 kind 节点被
停掉，结束后再启动。

## 摘要

- **fit 排名第一，98.8 分，并且每一项都领先**（第一次运行：96.6，S6 落后于 Alloy）。其后为 DataX 74.5、Alloy
  73.4、Telegraf 67.9、Filebeat 42.7、Promtail 39.6、Debezium 37.7、Canal 30.0、Kafka Connect 加 Camel 17.4。
- **S6，文件到 Loki**：fit 每秒 42.79 万行（第一次 27.89 万，+53%），用 0.48 核（此前 1.38），Alloy 为 43.16 万行、
  0.83 核：fit 达到其吞吐的 99%，CPU 只用其 58%，每 CPU 秒行数是其 1.71 倍；内存（40 MiB 对 129）和延迟（p99
  546 ms 对 1,344）都约为其三分之一。三个工具都停在 Loki 自身在服务器核上的上限附近（约每秒 43 万行）：fit 加大
  批次也不能再提高。
- **fit 每条记录的 CPU 回到 11-10 附近**，吞吐相同：

  | 项 | 11-10 | 11-11 第一次 | 本次 |

  （单位：核；本次 S3 为每秒 31.8 万行，11-10 为 29.9 万。）S1 的 1 KiB 行仍比 11-10 多 6% 到 9%。
- **S9 的延迟**：本次 p99 为 1,557 ms（第一次 2,408，11-10 为 1,597）。它随 fit 每秒一次的轮询与 SQL Server 每秒
  一次的捕获作业之间的相对位置而在运行之间变化（每个构建各跑九轮，在 1.4 到 2.4 秒之间），与 fit 的代码无关。
  默认 `poll_interval` 改为 500 ms（Debezium 的默认值）可以缩小这一波动，代价是空闲时查询更多：保持不变，留给
  用户决定。
- **S8**：Kafka Connect 的 Camel MQTT 5 源每一轮仍然丢消息。
