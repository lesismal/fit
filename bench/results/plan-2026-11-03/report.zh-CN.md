## 摘要

- **HTTP/3 现在随连接数扩展。** fit 的 HTTP/3 每请求 CPU 从并发 500 到 10,000 都保持在 3.1-3.2 µs，而 2026-11-02 时
  从 3.5 涨到 4.2：W0 HTTP/3 在 500 +12%、2,000 +19%、**5,000 +36%、10,000 +33%**（每秒 193 万和 187 万），并发 500 到
  5,000 与 nginx 持平（99-100%），10,000 为其 98%，之前是 73-85%。并发 100 时 fit 现在第一（+5.5%）。
- **API 网关在两种协议下都更快了。** W1 HTTP/1.1 每一档 +5% 到 +11.5%（并发 500 每秒 243,014，每请求 24.49 µs，之前
  26.58），h2 +3.5% 到 +6%；W5 +10.0% 和 +5.7%；W6 固定速率下每请求 CPU 少 2-12.5%。与 nginx 相比，W1 HTTP/1.1 为
  77-87%（之前 69-81%），h2 为 91-99%（之前 93-95%）。
- **fit 没有任何一项变慢。** 58 轮中 19 轮比 2026-11-02 快 3% 以上，没有一轮慢 3% 以上；吞吐中位数 +1.2%，每请求 CPU
  -2.0%。其他服务器的中位数为 +0.6% 到 +1.2%。
- **发现并修复了一项代价：** 大量请求经代理时 fit 的峰值内存上升（W1 并发 5,000 走 h2 时 415 MiB，之前 304）。A/B 定位到
  fit 的 d6bdf04：它的定时器让回收的 exchange 在池外仍被持有；fit 6305218 改为弱引用，HTTP/1.1 并发 5,000 时回到
  328-371 MiB（之前 372-399，d6bdf04 之前为 336-344），吞吐不变。本次方案运行时还没有 6305218。
- **2026-11-02 的 W6 尾延迟不是回退。** fit 在每秒 3 万走 h2 时的 p99.9（9.64 ms）是两种模式之一（约 3 ms 和约 10 ms），
  2026-10-30 的版本同样如此（下文 A/B）。

## 改了什么

fib 从 4b24cf3 到 3664a1e，合并了两个分支：

| 提交 | 改动 |
| --- | --- |
| de62b0b | HTTP/1 请求组帧和响应头只遍历一次头部 map；解析响应时顺带记下需要的字段 |
| e17bf98 | 字段值的控制字符检查一次 8 字节 |
| 540385b | 客户端只在行首查找 Transfer-Encoding |
| c92842d | 头部字段先按 8 字节前缀排序 |
| 2adf91e | 只在开启 trace 时才为读取字节数装箱 |
| 5693fff | 截止时间被清除或推后时保留连接的定时器，HTTP 服务器每个空闲超时才移动一次，而不是每请求两次 |
| d5a8804、48914bd | QUIC 把到期的 ACK 及随之发送的流控额度保留到一批请求的应答，最长 max_ack_delay，而不是 1ms；高负载下 1ms 保留有 15% 的批次过期，之后每个应答都单独一个数据报（并发 5,000 时每收 1 个发 1.82 个，之后 0.65 个）。上传进行中的数据仍保持 1ms |
| 248ca81、84f0931、69bdf4d | HTTP/3：响应头检查与计算大小合为一次遍历；每轮 QUIC 调用只读一次时钟；请求自身字段直接查找、不再规范化 |
| 9258b9a | 发送包的帧记录超出内联容量后从池中取 64 帧数组，应答 25 个请求的包不再每包分配 4 次 |

fit：e5b8675（Connection 的 `keep-alive`/`close` 不再规范化，Forwarded 的 host 手工加引号）、d6bdf04（回收的 exchange
保留其截止定时器）、6305218（该定时器弱引用 exchange）。

每项在保留前都用 `bench/ab.sh` 单独测过，数字在各提交说明里。

## 剩下的

- **W1 HTTP/1.1 为 nginx 的 77-87%。** 内核开销与 nginx 相同（每请求各约 7 万周期，fit 的系统调用更少）；差距在 fit 的
  用户态：每请求 6.1 万周期、8.4 万条指令，nginx 为 2.6 万和 3.4 万，分散在头部 map（8%）、头部的序列化与解析（各 5%）、
  定时器、池、分配与 GC（各 2-3%）。下一步是结构性的：代理两侧以字节形式透传头部块，不再在每一侧构建、排序、写出 map，
  估计约 5%，需要 fib 新增 API。
- **网站走 HTTP/3 为 nginx 的 52-83%**，是按字节的开销，不是按连接：AES-GCM 占 fit 在此场景 CPU 的四分之一，而 Go 1.27
  的 amd64 GCM 没有 VAES 路径，OpenSSL 在 Zen 4 上用了；带 GSO 的 UDP 发送又占五分之一。
- **W1 在并发 5,000 到 10,000 时的峰值内存**，385-650 MiB，nginx 为 221-411（6305218 之前）。
- **W6 p99.9 背后约 10 ms 的停顿**（见上文）。

## 说明与局限

- 单机、回环、每项一轮：单轮几个百分点在噪声之内；HTTP/3 和 W1 的提升在每一档都成立。
- 代理定时器的内存修复 6305218 是用 A/B 测的，不在本次方案中。
