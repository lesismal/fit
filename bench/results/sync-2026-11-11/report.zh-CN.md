# 同步基准测试，2026-11-11：基于 fib aabd7c2 的完整计划，含 S10 与 Alloy

[English](report.md) | [简体中文](report.zh-CN.md)

同步计划的十项在基准测试主机上运行（Ryzen 7 7800X3D，8 核 16 线程，Linux 7.0，Docker 29.1.3），工具与规则同
[2026-11-09 的计划](../sync-2026-11-09/report.zh-CN.md)：每次只跑一个搬运工具，占用同样的四个物理核，每项 3 轮；
每张表及其权重与每行得分见 [tables.md](tables.md)，排名见 [scores.md](scores.md)，各项的 JSON、日志和 fit 的
profile 在旁边。fit 构建于 `1f794c1b`（fit main `3881490b`，fib `aabd7c2`；main 之后直到 `a9fbe573` 的提交不涉及
这些项运行的路径）。运行期间主机的 LLM 服务（strata）和一个 kind 节点被停掉，结束后再启动。相比
[11-10](../sync-2026-11-10/report.zh-CN.md) 的新内容：S10，MQTT 到 InfluxDB，对比 Telegraf 1.40.3（权重 5%，取自
S1，S1 现为 15%）；S6 在 Promtail 之外加入 Grafana Alloy 1.21.3。

## 摘要

- **fit 排名第一，96.6 分**（11-10：98.8，权重不同且无 S10），领先 Alloy（85.6，仅 S6）、DataX（72.2）、Telegraf
  （70.6，仅 S10）、Promtail（45.1）、Filebeat（43.4）、Debezium（37.5）、Canal（30.5）以及 Kafka Connect 加 Camel
  （17.8）。除 S6 外，fit 在每一项得分最高。
- **S10，MQTT 到 InfluxDB（新增）**：每秒 8.19 万条读数，是 Telegraf 6.25 万的 1.31 倍，用 1.76 核对其 1.81 核，
  18 MiB 对其 53 MiB；延迟相同。
- **S8**：Kafka Connect 的 Camel MQTT 5 源每一轮仍然丢消息（50 万中分别丢 39、2、23 条）。
- **fit 落后之处，或自 11-10 以来退步之处：**
  - **S6，文件到 Loki：Alloy 领先。** 每秒 43.16 万行，fit 27.89 万（fit 为其 65%），用 0.84 核对 fit 的 1.38 核
    （fit 每 CPU 秒行数为其 39%）；fit 的内存（40 MiB 对 129）与延迟（p99 464 ms 对 1,363）更好。fit 在此项得
    67.1 分，是唯一没有领先的一项。
  - **自 11-10 以来，fit 每条记录的 CPU 增加了 8% 到 20%**，吞吐相同：S1 从 0.99 核到 1.18 核（每秒 91.3 万行，
    128 字节行），1.26 → 1.48（1 KiB），S3 2.23 → 2.40，S5 0.70 → 0.76，S9 1.52 → 1.83（行数多 17%）。其他工具的
    CPU 没变（Filebeat 2.17 → 2.18），所以是 fit 自身的。profile 显示多出的部分在垃圾回收（`runtime.scanObject`，
    约占 S1 CPU 的五分之一）：自 11-10 以来记录增加了字段（`Record.Origin`、流水线名与世代、变换编号），变大了。
  - **S9 的延迟 p99 从 1,597 ms 升到 2,408 ms**（Debezium 1,498），而吞吐升到每秒 34.4 万行（Debezium 9.4 万的
    3.7 倍）。原因尚未查明。
- 其余与 11-10 持平：S2、S4、S5、S6、S7、S8 的吞吐相差在 ±2% 以内，S1 最多 +6%，S3 +6%。
