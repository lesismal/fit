# M2 report, 2026-10-20

Benchmarks at the end of M2 (dynamic config and TLS, I24–I35), on the same Linux host and with the
same harness settings as the [M1 report](m1-report-2026-10-19.md), with fit at commit 59083f3 and
fib's `main` at 8c637e0 (after v1.5.3). M2's exit tests are functional and pass in CI (I35); this
report is the comparison with nginx that the progress notes left for the end of M2.

- fit still meets every M1 target in the [roadmap](../../docs/roadmap.md#performance-targets), and
  no throughput scenario got slower through M2.
- Static files are much faster than at M1: 1.33 times over HTTP/1.1 and 1.84 times over h2c,
  from R05's asynchronous sending and R05b's sendfile.
- The proxy is at 86% of nginx over HTTP/1.1 (83% at M1) and 94% over h2c (92%), using 1.5 and 1.3
  times nginx's CPU per request.
- The access log and request metrics are off by default. Turned on, they cost the fastest paths
  25% and 14% (fixed over h2c), as R07d and I34 measured. The remedy is in fib
  ([A17](../../docs/fib-api-requests.md#a17-cheaper-onfinish-and-setvalue-on-every-request),
  [A18](../../docs/fib-api-requests.md#a18-a-responses-status-and-when-its-request-arrived-without-a-hook)).

## Results by scenario and protocol

One table for each scenario and protocol, with a row for each server, ranked by throughput (TPS),
then CPU efficiency, then memory efficiency:

- **TPS**: requests a second.
- **CPU EER**: requests per CPU-second, throughput for each core the server kept busy.
- **MEM EER**: requests a second for each MiB of the server's anonymous memory,
  at the end of the run.
- Each ranked value is followed by its share of the best in its column, floored, so that only the
  best reads 100%.
- **Latency**: wrk's p99 over HTTP/1.1, and h2load's mean and maximum otherwise, since it reports
  no percentiles.
- **CPU**: the cores the server kept busy, of the 7 it was pinned to.

The tables are rendered from the run's JSON by [`benchreport`](../cmd/benchreport).

### Notes

nginx, Caddy and Traefik are within 2% of their M1 numbers, so the host and the load generators
measure as they did. fit's fixed response over HTTP/1.1 and its static file over HTTP/1.1 come out
at about the same rate, 780k: wrk on seven CPUs is what holds them there, as I34 noted, not fit.

fit's two rounds alone (the `m2-2026-10-20-fit-*.json` files) agree with the run above within 1.5%:
fixed 771k and 777k over HTTP/1.1, 3,814k and 3,816k over h2c; static 777k and 780k, 2,446k and
2,450k; proxy 228k and 227k, 237k and 237k.

fit's p50 over HTTP/1.1 is close to nginx's or below it (fixed 0.17 ms against 0.15, static 0.16
against 0.55, proxy 1.06 against 0.95); it is behind in the tail: p99.9 3.9, 3.2 and 5.8 ms against
nginx's 2.3, 0.8 and 2.0.

nginx preallocates its connection tables (`worker_connections 65536`), which shows before any
connection opens.

## The proxy against nginx

| Protocol | nginx | fit | fit / nginx | CPU per request, nginx | fit | fit / nginx |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| http/1.1, M1 | 258k | 215k | 83% | 18.1 µs | 28.5 µs | 1.57 |
| http/1.1, M2 | 264k | 226k | 86% | 18.0 µs | 26.8 µs | 1.49 |
| h2c, M1 | 249k | 230k | 92% | 22.4 µs | 29.0 µs | 1.29 |
| h2c, M2 | 253k | 238k | 94% | 22.0 µs | 27.9 µs | 1.27 |

CPU per request is the server's cores over its requests a second. R07a–R07c took fit's proxy from
215k to 226k over HTTP/1.1, as R07c's own runs found (228k). nginx does not use the server's seven
CPUs over HTTP/1.1, so its rate here is not bounded by its CPU, and what fit has left to gain is
in its CPU per request, half as much again as nginx's over HTTP/1.1: the proxy's exchange in fit, and fib's client and
server under it. That is for a profiling iteration, not for this report.
